# API worker package

Scope: `packages/api-worker/**` only. Engine rules live in `packages/game-engine/AGENTS.md`; client rules in `packages/web/AGENTS.md`; shared workflow, commands, and gates in the root file.

## Identity and entrypoint

- Hono app (`packages/api-worker/src/index.ts`). Each handler file exports a route group; the entrypoint composes them, applies CORS and error handling centrally, and re-exports the room Durable Object class and the declared workflow classes.
- Route groups stay with their owner under `features/*`, `games/*`, or `platform/*`. There is no shared root schema directory.
- TypeScript `~6.0.3`, Zod `^4.4.3`, Vitest `~4.1.10`, Wrangler `^4.147.0` (see `package.json`). The worker config is standalone: `strict: true`, `noEmit: true`, no `noUncheckedIndexedAccess`.

## Runtime bindings (`wrangler.toml`)

- D1 database `DB` (`werewolf-db`); Durable Object bindings `GAME_ROOM` (`GameRoom`) and `WECHAT_AUTH` (`WeChatAuthProxy`); R2 buckets `AVATARS` (`werewolf-avatars`) and `GAME_MEDIA` (`werewolf-game-media`).
- Rate limits `ROOM_LOOKUP_LIMITER`, `ANONYMOUS_SIGNUP_LIMITER`, and `WORD_SUBMISSION_LIMITER`; Analytics Engine datasets `LOAD_TIMING`, `AI_USAGE`, `REQUEST_TRAFFIC`; five workflow bindings (`fib-word-supply`, `undercover-word-supply`, `drawguess-word-supply`, `decrypto-word-supply`, `word-submission-review`); cron triggers every 5 minutes and at 03:00 (saga reconciliation, expiry/cleanup). The 04:00 automatic word-supply dispatch was removed; the manual `POST /games/words/trigger-supply` still dispatches the same workflows. External submissions are isolated in `features/wordSubmissions`; their review workflow never publishes. See `docs/agent-word-submissions.md`.
- `compatibility_date` is `2026-10-01`.

## Room authority: Durable Object and its SQLite storage

- Composition root: `packages/api-worker/src/app/GameRoom.ts` resolves game modules and is exported as the `GameRoom` Durable Object class. `GameRoomRuntime` owns the state store, effect outbox, command pipeline, and gateway.
- Room authority state lives in the Durable Object's own SQLite storage, accessed via the storage SQL API, never via Drizzle. Tables are `room_state`, `command_receipts`, `effect_outbox`, `effect_replays`.
- There is no storage migration chain or schema-version table. On wake, non-empty storage is retained only when the table names and columns exactly match the current structure; otherwise it is discarded and recreated (rooms are short-lived sessions). Game state is parsed directly using the current game codec; there is no per-game state version or read-time migration. The D1 `rooms` table is only the room directory (metadata and saga state), not authoritative game state.

## Effect outbox, recovery, and state reads

- Effects are inserted in the same transaction as the committed command. The single Durable Object alarm drains due effects and sweeps stale sockets. Dedupe is on `(scope, game_type, effect_type, business_key)`. Retry policy: at most 7 attempts, 2-second base doubling to a 5-minute cap, 2-minute delivery watchdog. Failed effects can be replayed through the admin recovery surface (`features/admin/effectRecovery.ts`).
- `RoomStateStore.read()` selects the current game module from `game_type` and parses the stored JSON through its codec. Invalid shape or game identity throws immediately; the worker does not rewrite state or command receipts to migrate game data.

## D1 and Drizzle

- D1 is the relational store; Drizzle is the typed query layer over it (`createDb` returns `drizzle(d1)`, schema-free). There is no Drizzle Kit, no Drizzle config, and no generated schema directory.
- Migrations are hand-written SQL files applied by Wrangler: `0001_init.sql` through `0097_word_submission_catalog_fk.sql`, with no `0002` file.
- 43 tables are declared exactly once via `sqliteTable` in owner `dbSchema.ts` modules, pinned by `declares every physical D1 table exactly once in its owner module` in `contracts/architecture.contract.test.ts`. Further tables exist only as raw SQL in migrations; check the migrations before claiming the full physical set.
- Growing value sets (the game list, word-library games, word categories) are lookup tables referenced by foreign key: `game_types`, `word_games`, `word_categories`. Never encode them in a CHECK constraint, pinned by `new migrations never encode game or category lists in CHECK constraints` in `contracts/d1MigrationRules.contract.test.ts`. The code constants are the only authority and the tables are their projection; the runtime reads the constants, not the tables. Pinned in `contracts/d1Catalog.contract.test.ts` by `game_types rows equal GAME_TYPES in order`, `word_games rows equal GAME_WORD_GAMES`, and `word_categories rows equal each engine category catalog`; `rejects unregistered games and foreign categories` pins the foreign keys.
- Adding a game is one migration inserting its `game_types` row. A word-library game's `word_games` and `word_categories` rows land with the change that adds it to `GAME_WORD_GAMES` / `WORD_CATEGORY_CATALOGS` (its supply migration), never ahead of the code. `pnpm new-game` writes the registration only after replaying the current migrations in `node:sqlite` and checking the resulting schema, and refuses (non-zero exit) when the id or its stats table already exist, a lookup table is missing, or a CHECK hard-codes a game list (pinned in `scripts/new-game.test.mjs` by `refuses a game id that the current schema already registers in game_types`, `refuses to generate when the current schema hard-codes a game list that would need a rebuild`, and `refuses when a lookup table is missing from the replayed schema`); such cases are hand-written under the rules below. A `--word-category` list that breaks the engine rule is refused as an input error under its own heading; fix the arguments instead. Its output, like any earlier migration, is a starting point, never a template: review every migration against the current schema and this change's requirements before committing. Adding a category is a catalog edit plus one migration inserting its `word_categories` row; changing a category's display name is one `UPDATE` of `name`, while changing its `id` is rejected by the child tables' foreign keys and needs a hand-written migration. None of these rebuilds a table.
- Start a migration with `PRAGMA defer_foreign_keys = true;` only when it needs deferred checks, and never reset it to `false`: resetting discards unresolved violations instead of failing the commit. Pinned by `new migrations never reset defer_foreign_keys` in `contracts/d1MigrationRules.contract.test.ts`.
- Lookup-key CHECKs (`game_types.id`, `word_categories.id`/`name`) are the SQL projection of the engine's single rule in `packages/game-engine/src/platform/protocol/catalogIds.ts`; change both together. Pinned by the `key shapes` sweeps in `contracts/d1Catalog.contract.test.ts`.
- D1 caps a LIKE or GLOB pattern at 50 bytes and evaluates a CHECK's pattern only when a row is written, so a migration can apply locally and fail on the first production write. Write every pattern as a literal operand (`x GLOB '<literal>'`, no `glob()`/`like()` calls) of at most 50 bytes, pinned by `every LIKE and GLOB pattern is a literal within D1's 50-byte limit` in `contracts/d1MigrationRules.contract.test.ts`; use `trim(x, char(...))` or `instr` for character sets.
- The same 50-byte cap applies to runtime SQL: a LIKE/GLOB pattern bound or built from user input fails with "pattern too complex" once the input is long enough (about 16 CJK characters inside `%…%`). Runtime patterns are literals too, and substring search over user input uses `containsIgnoringAsciiCase` in `src/platform/storage/substringSearch.ts` (`instr` over `lower()`, no length cap, `%`/`_` literal, ASCII case-folding like LIKE). Pinned by `writes every runtime LIKE/GLOB pattern as a literal of at most 50 bytes` in `contracts/architecture.contract.test.ts`, which reads every string/template literal and `+` chain in the production files under `packages/api-worker/src` (not `functions/`, which holds no SQL) as the SQL it builds (any run-time value, inside quotes or not, makes the pattern computed) with the migration rules' lexer, and rejects Drizzle's `like`/`ilike` operators, imported or re-exported, and `* as` forms of drizzle-orm. Write worker SQL keywords in upper case. The rule reads an upper-case LIKE/GLOB in any literal, and a keyword in any case when a bind parameter, string, `(` or call follows it, so lower-case `like ?` is caught wherever the literal sits while prose such as "looks like a bot" is not; a lower-case keyword followed straight by an interpolated value reads like prose and is left to the upper-case rule.
- Rebuilding a parent table (`CREATE TABLE <t>_next`, copy, `DROP`, `RENAME`) must rebuild every foreign-key descendant in the same file, with each child `_next` referencing the parent `_next`, and must first `DROP` and finally recreate verbatim every trigger that references a rebuilt table. With foreign keys on, `DROP TABLE` runs an implicit `DELETE` whose cascades are not deferred, so a missing descendant loses data or fails the migration. Copy tables that carry generated columns with an explicit column list. Pinned by `every rebuilt parent table rebuilds all foreign-key descendants and referencing triggers` in `contracts/d1MigrationRules.contract.test.ts`.
- A migration that rebuilds a table or moves data is verified by rehearsing it on a copy of production data before merge, not by a dedicated long-lived test: export production read-only (`wrangler d1 export` or `SELECT`), apply the pending migrations to the copy in Wrangler order, run `PRAGMA foreign_key_check` (must be empty) and `PRAGMA integrity_check`, and compare row counts table by table before and after, accounting for every intended difference. The PR body records the results and the copied row counts used for the write estimate. Do not keep tests that replay an applied migration to check how it moved data; the sha256 manifest freezes applied files, and functional and contract tests run on the full migration chain.
- When rebuilding a table, also compare its indexes, constraints, and triggers before and after the migration; preserve required ones or document intentional removal. Register critical word-supply index prefixes in `src/platform/wordSupply/__tests__/wordSupplyIndexes.contract.test.ts` and keep the affected query's row-budget test.
- Migration files that have been applied in production are immutable, pinned by `migration files match the recorded sha256 manifest` in `contracts/d1MigrationRules.contract.test.ts`: every migration file is recorded with its sha256 in `contracts/d1MigrationManifest.json` (Wrangler order), a new migration must be added there, and changing a recorded file fails the test. `pnpm new-game` records its registration migration itself. Wrangler records applied migrations by file name only (`d1_migrations` holds name and applied time), so an unapplied migration already merged to main (for example after `Apply D1 migrations` failed) that must change is deleted and replaced by a new file, never edited in place, and the deletion needs the user's approval; a migration that exists only on an unmerged branch is edited in place with its manifest entry.
- When adding or changing a D1 query, examine its filters, joins, ordering, indexes, and invocation frequency, including retries and scheduled jobs. For queries on growing tables or high-frequency paths, use `test/rowCountingDb.ts` against migrated D1 to test realistic small and larger datasets and assert a justified read/write budget; verify the query plan when useful. A small fixture or a correct result alone does not establish a cost bound.
- Before adding an index, compare the expected read savings with ongoing write amplification and one-time build costs, using representative query and insert/update/delete frequencies; state any unknowns rather than assuming a net saving. For critical write paths, measure and assert a justified `rows_written` budget with `test/rowCountingDb.ts`; verify actual usage after deployment because local measurements do not establish production billing.
- Review all pending migrations for a release together: consolidate successive changes to the same table before first remote application so it is rebuilt as few times as constraints allow, and create indexes only on final tables, not intermediate tables that will be replaced.
- D1 runs on the free plan: 100,000 rows written per day, reset at 00:00 UTC. A migration PR body states the one-time write estimate (copied rows × (1 + indexes on the table), plus index builds and seeds), marked as an estimate because local tests do not measure production billing. Merging deploys and deploying applies every pending migration on main, so merge a migration PR only in a freshly reset window with enough headroom, and run no bulk submission, review, publication, or other merge in that window until the migration is applied and verified.

## Worker game catalog and modules

- `WORKER_GAME_CATALOG` is exhaustive: exactly one worker module per entry in `GAME_TYPES`, in the same order, pinned by `registers exactly one Worker module for every canonical game type` in `packages/api-worker/src/games/__tests__/catalog.test.ts`. Each module binds the engine, state codec, public/internal command schemas, effect schema, and HTTP routes.
- HTTP routes are projected from the same catalog, pinned by `projects game-owned HTTP routes from the same catalog` in `packages/api-worker/src/games/__tests__/catalog.test.ts`. A game declaring a workflow must also re-export it from the entrypoint and declare the workflow binding in `wrangler.toml`.

## HTTP patterns

- Validate JSON bodies with `jsonBody(schema)` (`platform/http/`). It returns HTTP 400 with `{ success: false, reason: 'VALIDATION_ERROR', detail }`.
- `callDurableObject` translates Durable Object errors into HTTP errors (503 retryable, 429 overloaded). Central error handling in the entrypoint catches HTTP errors, syntax errors, and generic errors; handlers do not need their own translation for these.
- `requireAuth` authenticates the current principal and sets `c.var.userId` and `c.var.isAnonymous`. Zod 4 is the schema library (`z.email()` and friends); seat schemas use the established `z.coerce.number().int().min(0)` shape for werewolf seats.
- The realtime gateway upgrades WebSocket connections to the room Durable Object stub and runs the v2 `SYNC`/`SYNC_RESULT` exchange (see the engine file for the wire protocol).

## Scripts, migrations, and gates

- Verified scripts in this package: `dev`, `dev:test`, `deploy`, `db:migrate:local`, `db:migrate:remote`, `db:seed:local`, `types`, `types:check`, `typecheck`, `test`. Migrations run before deploy in CI (see `.github/workflows/ci.yml` for the verified job order). This package has no `lint`, `format`, `knip`, or `build` script; those gates apply through the root configs and root tasks. `typecheck` runs the Wrangler types check first, then the main config, then the test config.
- Apply migrations locally with `db:migrate:local` and remotely with `db:migrate:remote`; both use the `werewolf-db` database and the package's Wrangler config. D1 migration rules are in the D1 and Drizzle section above.

## Secrets and logging

- Secrets inventory: `wrangler.toml` `[secrets] required` (11 names) plus `.github/workflows/` (7 distinct `secrets.*` names, 6 beyond the wrangler list), regenerated at the time of writing.

Its `error()` also reports to the error-reporting service. For client logging rules, see `packages/web/AGENTS.md`.
