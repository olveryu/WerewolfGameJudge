# 新游戏 UI Mock 设计

## 已确认的需求

- 讨论的 mock 是新游戏的页面/UI 原型，用于提前查看效果，不是测试中的 mock。
- 游戏实现之前和实现之后都需要查看 mock。
- 原型需要切换不同阶段和角色、打开弹窗并展示关键状态，不要求从头玩完整游戏。
- 最在意避免遗漏现有公共组件，例如座位区、操作手牌、菜单和弹窗。
- 公共组件默认保持生产环境当前样式和行为，但偶尔需要比较新样式。
- 预览使用离线假数据；真实联机另行验证。
- 第一阶段同时覆盖游戏首页、配置页和房间等完整页面，而不是只覆盖房间。
- 使用预设的公共页面和状态清单，由 AI 逐项确认对新游戏是否适用，以减少遗漏。
- AI 在交付 mock 时列出不适用的清单项及其原因，供用户检查。
- 使用项目内统一的本地预览入口查看 mock，不需要每次生成独立 HTML。
- 新游戏专属 UI 尽量做成正式版可复用的组件；mock 阶段先接假数据。
- 速度优化优先针对 AI 制作每个新游戏 mock 所需的时间。
- 首先用秘密希特勒做样板，对照真实页面验证预览。
- 新游戏 mock 默认使用预览入口和核对清单；特殊情况可以说明原因后例外。

## 已核实的现状

- [游戏首页](../packages/web/src/routes/home/HomePage.tsx)读取登录状态并使用路由；
  秘密希特勒的[首页配置](../packages/web/src/games/secrethitler/home.ts)只提供游戏信息，
  并不是单独的首页组件。
- 秘密希特勒的[游戏模块](../packages/web/src/games/secrethitler/module.ts)使用共享配置
  schema。[配置表单](../packages/web/src/features/room/config/GameConfigForm.tsx)是
  展示组件，但[配置页面](../packages/web/src/features/room/config/createGameConfigScreen.tsx)
  还依赖路由、房间连接及提交状态。
- [房间页面](../packages/web/src/games/secrethitler/room/SecrethitlerRoomScreen.tsx)
  使用真实的 [RoomShell](../packages/web/src/features/room/components/RoomShell.tsx)，
  但入场流程和房间状态 hook 依赖登录及房间会话。直接渲染外壳能复用座位和手牌，
  不代表自动覆盖所有游戏提供的内容和条件状态。
- 项目已有本地 `admin-mock` 模式和 mock 服务，但这不是现成的游戏房间预览；
  可借鉴其仅开发环境启用的方式，不必假定它能模拟房间连接。

## 已确认的方案

1. **统一预览入口。** 在 web 项目中增加仅本地开发使用的入口，选择游戏、页面、阶段、
   角色及预设状态；生产构建不可访问预览入口，也不调用真实后端。
2. **优先接真实页面。** 首页使用真实首页及虚构账号数据；配置页使用真实 schema、
   配置表单和页面布局；房间使用真实 RoomShell 和游戏页面内容。通过本地数据与
   明确的交互替身隔离登录、路由、提交和房间连接；不能直接复用的部分先评估并做最小
   拆分，不重画已有公共组件。具体拆分位置需在实现前进一步验证。
3. **场景数据而非复制 UI。** 为各页面维护虚构数据与关键状态，包括不同权限、弹窗和
   适用的游戏阶段。切换状态不运行完整游戏；模拟操作只改变本地预览状态，不发送真实命令。
   新游戏尚不存在的专属 UI 独立编写，尽量让正式页面复用；未实现的部分明确标记。
4. **公共清单。** 以首页、配置、房间、公共弹窗和关键权限状态组织清单。每个新游戏
   标记已覆盖或不适用；不适用项附原因供用户检查。清单不保证自动发现所有游戏专属状态。
5. **样板与复用流程。** 先接入秘密希特勒的首页、配置和房间，以同一状态对照真实页面，
   逐项核对公共内容。随后更新新游戏工作流，默认使用预览入口和清单，而不是手写
   一次性整页 mock。
6. **探索新样式。** 默认展示当前生产组件；如需比较新样式，在预览内隔离候选变体，
   不改变默认生产样式。具体隔离方式按要探索的组件决定，不预先复制整套组件。

## 验证与边界

- 对照秘密希特勒真实页面，覆盖首页、配置页、房间、代表性的阶段、权限和弹窗；
  检查移动端和桌面布局，并记录清单中的不适用项。
- 检查离线状态下预览和状态切换可用、无真实网络命令，且生产构建不暴露预览入口。
- 记录样板制作及之后新游戏 mock 的耗时，和以往方式比较；目前没有可靠基线，
  不能承诺具体提速倍数。
- 不以预览替代真实联机、完整游戏规则或正式测试；复用真实组件也不能单独保证所有状态
  均已覆盖。

## 本地预览与清单

运行 `corepack pnpm --filter @game-judge/web run dev:game-preview`，打开
`http://localhost:5187/preview/`。预览使用独立端口的浏览器存储、虚构账号和内存房间；
关闭进程后内存状态丢失。页面中的网络请求会被拒绝，房间命令只由本地引擎处理。
更换阶段或视角会重置房间到该预设；选择机器人座位时，预览将该座位替换为虚构玩家。
预览不会处理后端定时任务、奖励或真实联机，不应将模拟链接用于分享。

秘密希特勒是首个样板：工具栏可打开真实首页、创建配置页和房间页面，选择已生成的
游戏阶段及各座位视角。房间内配置可保存到模拟状态；创建房间、账号和音乐设置等
依赖真实服务的操作尚不支持，会明确报错或提示；不是所有首页链接都已接入预览。
真实页面运行在独立预览框架中，强制弹窗不会挡住预览控件；切换阶段或视角时，
预览框架会重新加载并回到工具栏所选页面。

接入新游戏时，在 `packages/web/preview/` 声明游戏、阶段、视角和页面组件并注册到
`previewGames`；通用选择器和预览框架不需要重写。游戏未实现时，场景可由虚构数据
驱动，页面应直接复用已有公共组件；已实现后应复用真实页面及其状态投影。

### 秘密希特勒样板清单

- 已接入：真实首页、选游戏、创建配置页、房间；真实房间的座位、手牌、房主菜单、
  游戏信息和弹窗随所选场景呈现。12 个游戏阶段和 8 个座位视角可切换。
- 未覆盖：创建房间、账号和音乐设置、首页其他产品页面、后端定时推进及奖励；
  这些依赖的服务未接入离线替身，不应误认为不适用。
- 需继续按场景核对：身份卡、角色操作、公共结果、复盘、分享等各弹窗的具体内容和
  权限组合；单个阶段样例不等于穷举其所有状态。

新游戏 mock 交付前，按实际游戏逐项列出已覆盖状态及不适用项和原因：

- 首页与选游戏：游戏入口、素材、名称、导航。
- 配置：创建和房间内编辑、字段、默认值、可用和不可用状态、返回和确认。
- 房间：标题、连接状态、座位及玩家信息、房主与普通玩家、不同阶段、
  操作手牌、房主管理、设置和玩法入口。
- 弹窗：身份或私密信息、玩法、配置、玩家信息、分享，以及该游戏适用的操作和结果。
- 游戏结束：结果、复盘、重新开始和相关权限；还需核对游戏自身的阶段与特殊状态。

真实组件的条件渲染由场景数据决定；清单不是自动覆盖证明。对照真实页面和游戏规则
核对，未完成的状态应标为未覆盖，不能当作不适用。

## 实施状态

样板已接入并完成基础验证；真实联机页面的逐项对照及更多弹窗场景仍待完成。

### 骰子模拟器试验

这是验证未实现游戏如何接入预览的离线样板，不是正式游戏。每人一个六面骰盅，
可自行调整下次摇骰数量（默认 5 颗），自行摇骰和查看；玩法、叫点、计分、
输赢和惩罚由玩家自己决定。预览中的 1–20 颗选择范围只是 UI 试验，不是已确定的
正式产品限制。摇骰后默认仅当前视角可见；线下玩家自行展示，不提供亮骰功能。
摇骰时播放示意性的骰盅动画和可关闭的合成音效，停下后需自行掀开骰盅查看；
动画不是物理模拟，也不能用于验证随机性或实际联机隐私。系统要求减少动态效果时，
跳过摇动动画，仍可查看结果。
玩家通过一张「骰子」手牌打开共享房间弹窗，摇骰和查看均在弹窗内完成；
关闭弹窗不会重置本次结果。
掀开后可点击任意骰子固定点数，再摇时保留选中的骰子；再次点击取消固定。
数量在下次摇骰时生效，不能减少到已固定骰子数以下。
若先减少数量再固定更多现有骰子，数量会自动增加以容纳固定项。

- 已覆盖：真实首页、共享房间外壳、座位和行动手牌；房主开始、摇骰、调整数量、
  固定骰子，以及等待、进行中和已掀开骰盅视角。
- 尚未接入：首页的道具箱入口、正式配置页和创建房间、真实联机、玩家资料、
  分享、设置和房主管理的完整操作。配置页进入的是模拟房间，不创建真实房间。
- 预览切换视角会重置数据，不能验证跨玩家同步或真实联机隐私。没有预设玩法说明或游戏结算状态；
  是否需要这些页面留待正式产品设计。

### 抽牌与抽身份设计

**已确认：** 道具箱需要抽牌，其中包括抽身份；房主可以选择身份种类及每种身份的数量。
身份名称全部由房主自定义，不提供预设身份。骰子不需要亮骰功能，线下玩家自行展示。
房主可设置每名玩家能抽取的身份牌数量。
所有玩家共用一副身份牌，抽走后不放回，因此各身份在全场的数量不超过房主设置的数量。
抽到的身份仅抽牌者可查看，房主不能查看其他玩家的身份。
开始前身份牌总数必须不少于玩家所需总张数；不足时阻止开始并提示，多余的牌留在牌堆中。
房主可重开整轮，将所有已抽身份牌返回牌堆并重新洗牌；玩家不能单独退牌重抽。
重开只影响身份牌，房主可修改身份配置；骰子等其他道具保持现状，本局启用的道具不变。
同一个房间可同时使用多个道具，不必在创建房间时只选一种。
房主在配置页选择本局使用的道具，房间中向所有玩家展示所选道具。抽身份时玩家自己逐张点击抽牌，
直到达到房主设置的每人抽牌数量。
本局开始后道具选择锁定；要更改道具，需要重新开始游戏。
道具箱房间不显示座位表、不设置固定人数上限。进入房间后，玩家可通过行动手牌入座；
房主也自行选择是否入座。开始前可取消入座，至少有一人入座才能开始。
房间展示入座人数和当前在房间的总人数；总人数包括参与者和观众。
开始时锁定已入座的参与名单，之后进入的玩家为观众，只能观看公开信息，不能使用道具。
离开或重新进入房间不自动改变已锁定的参与身份；需要通过手牌展示自己的入座状态。
玩家关闭抽牌弹窗后，可以再次打开并查看自己已经抽到的身份牌。
每种自定义身份包含名称和可选的身份说明，房主为其设置数量。
创建房间前选择道具；开始时配置抽身份（如已选），然后确认开始。身份配置需要能够保存，
供下次复用；配置跟随账号，换设备也可使用。保存范围仅为抽身份配置，道具每次重新选择。
可以保存多套身份配置，每套可命名、选择和修改。
复用配置后的修改默认只影响本局；房主可主动更新原配置或另存为新配置。

**待讨论：** 重开一轮的确认提示；开始后是否显示「本局参与中」或「观看中」的状态文案。

**实施状态：** 已实现离线 mock：配置页选择道具并进入模拟房间，房间展示已选道具；
身份设置按标签切换，抽牌数量和总数固定展示。房主可配置和临时保存身份方案、逐张抽牌、
重新配置身份；工具栏有虚构身份示例。方案只存在当前预览页面的内存中，刷新或切换
页面、阶段、视角会清除；尚未实现账号保存或跨设备同步。预览仅模拟当前视角，
不能验证多人共用牌堆或真实身份隐私。道具箱为暂名，其他道具尚未确定。
mock 不显示座位表；房间中央展示游戏状态、当前视角的示例玩家形象和入座状态。形象复用现有头像及装饰组件，但使用示例数据；真实账号、装备和玩家资料交互留待正式开发。
当前视角可入座或取消入座，开始后锁定，观众不提供道具操作。
预览工具栏可设置其他在场人数和其中入座人数；应用新人数会重置预览。这些是虚构数据，
不是实时在线人数，不能验证真实玩家进出、断线重连或参与身份持久化。
