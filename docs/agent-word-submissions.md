# Agent 词语投稿

适用于 `fibking`、`undercover`、`drawguess`。Muse、其他个人助手和普通脚本使用相同协议，不依赖某家 Agent 产品。接口保存候选，不授予线上词库写权限。

## 1. 权限与审核边界

1. 管理员在「词库 → Agent 授权」签发独立凭证，设置游戏范围、每日投稿和未处理上限。
2. Agent 读取字段说明，预检，再把候选提交到隔离区。此时不调用模型，也不直接进入游戏词库。
3. 管理员在统一词库页的卡片流里审词，先对候选「批准进入审核」（endorse），再勾选并「启动独立审核」。独立 Workflow 复用各游戏现有审核器，但没有发布步骤。未经批准的候选不能直接启动审核（返回 `409`）。点错批准可用「撤回批准」（unendorse）把已批准项退回待批准，审核一旦启动就撤不回。
4. 管理员阅读原始材料、模型结论、独立资料和操作记录，明确「确认发布」后才进入游戏抽词库。

Agent 的自评、提示词和参考链接均为不可信材料，不是通过凭证。瞎掰王只从服务端固定 Tavily 接口搜索并提取独立发现的资料；不会请求 Agent 提交的 URL。模型仍可能判断错误，因此通过模型审核也不等于已发布。

待审、审核执行失败和模型未通过的候选均可由管理员单条或批量「人工通过」，不要求模型或独立检索先成功，也不强制填写理由；之后仍需单独发布。人工决定保存在 `approval_reason`（任何非 NULL 值，包括空字符串，均表示已人工通过）和操作事件中，不填造模型审核、证据或质量检查。原模型结论、版本、失败诊断保留。仅依赖模型结论发布时仍要求当前审核版本；显式人工通过不受模型版本或证据门槛限制。重新独立审核会清除原人工通过标记，必须根据新结果重新决定。

「批准进入审核」是另一道人工关口：只表示管理员看过并同意送审，不调用模型，不改变原审核结论，不写 `approval_reason`。批准记录在候选状态（`approved`）与操作事件中，不伪装成模型合规；批准后仍需启动独立审核，通过后单独确认发布。`pending`、`failed`、`rejected` 的候选均可批准；已批准的候选可直接审核，也可被拒绝。

后台沿用共享管理员口令，没有个人管理员身份系统。因此记录的是「共享管理员」或「审核工作流」，不声称识别具体操作者。

## 2. 凭证

- 每个 Agent 一个稳定身份。凭证由 32 个随机字节生成；数据库只保存 SHA-256 哈希和显示前缀。
- 完整 Token 只在签发响应和当前弹窗出现一次，不进入查询缓存、mutation 结果、浏览器持久化或日志。
- 有效期可选 30、90、365 天。暂停可恢复；撤销不可恢复。更换凭证立即使旧凭证失效，但不重置身份、日额度和待处理数量。
- 请求头：`Authorization: Bearer YOUR_TOKEN`。管理员口令在这些接口无效；投稿 Token 在管理接口无效。
- Token 丢失或创建响应不确定时，先刷新授权列表核对，再更换凭证；不要连续重复创建。不能取回旧 Token。
- 不要把 Token 放进 URL、公开仓库、截图或共享聊天。泄漏时立即撤销或更换。

## 3. 外部 API

以部署的 Worker API 地址为 `WORD_API_BASE`；不要使用前端页面地址。

| 方法 | 路径                            | 用途                                                           |
| ---- | ------------------------------- | -------------------------------------------------------------- |
| GET  | `/v1/word-submission-spec`      | 当前版本、授权范围、JSON Schema、分类及语义规则                |
| POST | `/v1/word-submissions/validate` | 逐条返回 `valid`、`duplicate`、`invalid`，不保存、不花模型额度 |
| POST | `/v1/word-submissions`          | 保存候选，成功返回 `202` 和完整批次                            |
| GET  | `/v1/word-submissions/:id`      | 查询本 Agent 的批次；其他 Agent 的批次返回 `404`               |

预检与保存之间仍可能出现重复或额度竞争；保存事务的结果为准。JSON Schema 不能完整表达繁简归一、拼音、同义身份等语义检查，因此应调用预检，不要只在客户端校验 Schema。

### 请求示例

```json
{
  "schemaVersion": 1,
  "game": "drawguess",
  "items": [
    {
      "clientItemId": "panda-001",
      "content": {
        "word": "大熊猫",
        "category": "animals",
        "difficulty": "easy",
        "potentialIssues": []
      }
    }
  ]
}
```

把请求保存到本地 `submission.json`，先预检：

```sh
curl --fail-with-body "$WORD_API_BASE/v1/word-submissions/validate" \
  -H "Authorization: Bearer $WORD_SUBMISSION_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @submission.json
```

预检通过后提交：

```sh
curl --fail-with-body "$WORD_API_BASE/v1/word-submissions" \
  -H "Authorization: Bearer $WORD_SUBMISSION_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: panda-batch-001" \
  --data-binary @submission.json
```

谁是卧底的 `content` 包含 `wordA`、`wordB`、`category`、`commonTraits`、`differences`、`potentialIssues`；瞎掰王包含 `word`、`definition: { coreMeaning, usageNote }`、`category`、`topic`、`references: [{ url, note }]`。实际分类、长度和数组要求以发现接口为准，不在 Agent 侧硬编码一份长期不更新的列表。

### 重试与错误

- 每批一个游戏，1–30 条，最多 128 KiB；字段严格校验，未知字段失败。批内 `clientItemId` 必须唯一。
- `Idempotency-Key` 是本应用明确约定的协议：8–96 个字符，首字符为 ASCII 字母或数字，之后允许字母、数字、`.`、`_`、`:`、`-`。不声称这是已定稿 RFC 的实现。
- 同一 Agent、同一 key、同一请求的重试返回原批次，不重复扣额度；对象属性顺序不影响请求指纹。修改请求后必须换 key。同一 key 配不同请求返回 `409`。
- 原批次重放即使全局暂停或额度已满仍有效，但凭证必须有效且 Agent 未暂停或撤销。凭证更换后，同一身份仍能重放原请求。
- `400`：结构、字段、版本、key 不合规；`401`：凭证无效或过期；`403`：权限或 Agent 状态不允许；`404`：无可见批次；`409`：幂等请求冲突；`413`：体积超限；`422`：有语义不合格项，整批不保存；`429`：速率、额度或容量不足；`503`：暂停收稿或基础设施暂不可用。
- 速率限流返回 `Retry-After: 60`。其他额度需要管理员处理或等待相应窗口，不要无限快速重试。网络结果不确定时保留同一个 key 与请求，查询/重试，不生成新 key。
- `202` 只表示已收稿，绝不表示审核通过或已发布。重放返回的是该批次当前状态。

重复检查复用每个游戏的身份归一。已在线词、完全相同的历史材料和批内重复不会进入审核；跨 Agent 只返回通用重复说明，不泄漏其他人的批次或身份。被拒绝的相同材料不会靠重新投稿绕过结论，应由管理员重新审核现有条目。

## 4. 管理界面

词库是统一单页，投稿卡片流是唯一的审核面（见[词库干净版方案](./word-library-clean-scheme.md)）。标题行有「+ 补词」与「Agent 授权」；点一张卡打开词条抽屉，审/发都在卡片流和抽屉里做，没有批次面板，没有 `?batch=` 深链。导航、筛选和分页替换当前后台历史条目。全局 header 返回进入后台的 Home/Room screen，直接打开后台时返回 Home。

- **投稿卡片流**：全局待审、待发布、失败数量；游戏、来源、状态选择面板；标题/分类搜索（LIKE，通配符按字面处理）；30 条一页的游标翻页。
- **批量栏**：在卡片流上方；「全选本页」只选当页可操作条目，支持半选，翻页不保留勾选，切换状态/游戏/搜索清空选择。勾选后批量栏按资格显示批准进入审核、启动独立审核、人工通过、确认发布、批量撤回批准、批量拒绝及数量；「批准进入审核」只处理所选待审、执行失败、模型未通过项；「人工通过」只处理所选待审、执行失败、模型未通过项，已经通过的候选不重复处理。未通过项不能混入发布。
- **管理员审核**：模型调用额度已取消，只留调用记录；审核不设应用次数上限，也不设单独的「强制」入口。确认后仍先记账、不退款、不重放供应商调用，不绕过供应商限额、内容规则、陈旧选择或审核结论。审核不会自动发布。对未批准的候选启动审核返回 `409`（选择过期或状态不符），须先批准再审核。
- **词条抽屉**：原始材料与独立结论分区；底部固定操作；显示实际审核模型/版本、人工决定、最近操作。发布、拒绝、人工通过、下架都有确认；原因一律选填，不填也能提交。人工通过不调用外部服务，不会自动发布。待审候选没有「启动审核」，只有「批准进入审核」；已批准或审核失败的候选才有「启动审核」。
- **授权**：新建、查看、修改名称/说明/游戏范围/每日与未处理上限/有效期、暂停/恢复、永久撤销、更换。修改不更换凭证、不重置已用量；有效期默认保持，选定天数后从保存时重新计算。未处理上限不得低于当前未处理量。已撤销授权可从列表删除，已有投稿和审计仍保留，删除后不计入可见授权容量。单次凭证弹窗要求明确保存后关闭，复制失败在弹窗内提示。
- **刷新**：沿用后台手动刷新策略，不轮询。后台任务运行时点击「刷新审核进度」；若启动响应不确定，可「确认审核任务启动」，不会创建第二次模型尝试。

确认启动时会检查已有 Workflow 的实际状态：无法确认或状态未知返回 `503`，继续使用原命令重试；已失败或已终止的任务返回 `409`，并将仍在审核的候选原子收尾为失败。刷新批次后由管理员重新发起审核，不重启旧实例。加载阶段的失败同样记录；若当时数据库故障使收尾也失败，可通过确认启动恢复，审计和修订号不会因重复恢复而重复写入。

管理员命令绑定内容指纹和修订号。陈旧选择整批失败，不部分发布；同一个命令重试使用同一 UUID 和冻结的请求。发布/下架使用同一个 D1 原子事务，下架只改变可抽状态，保留原始编号、来源、序列和账号已见历史，不能借重新上架重置历史。

迁移 `0077_submission_agent_archive.sql` 增加授权删除时间和仅索引可见授权的部分索引；新索引写入只影响可见授权的创建和删除，使历史授权增长不拖慢列表及容量检查。它同时扩展授权审计事件种类，复制既有控制审计表并保留事件编号、自增序列、外键、约束和原有四个审计触发器，新增参数、有效期与删除审计。一次性复制读写量与既有控制审计行数成正比，索引构建与授权行数成正比；上线前确认生产规模及费用，先迁移再部署。它不重建投稿、词库或游戏状态。

迁移 `0079_word_submission_endorsement.sql` 给投稿条目加 `approved` 状态与 `endorse` 动作（表复制重建，含身份索引与计数触发器）；`0080_word_candidate_approval.sql` 给三款游戏的候选表加 `approved` 状态与 `word_candidate_approvals` 审批记录表；`0081_editorial_model_operation.sql` 给模型调用账本加 `operation`（生成/审核）分项；`0082_word_candidate_list_index.sql` 给三张候选表加（状态，创建时间，编号）列表索引；`0083_word_candidate_dismissal.sql` 给候选拒绝记 `word_candidate_dismissals` 审计表（按请求编号加创建时间索引）；`0084_word_submission_unendorse.sql` 给投稿动作加 `unendorse`（撤回批准，表复制重建，审计事件行与外键保留）。迁移 `0085_drop_dead_candidate_tables.sql` 删除六张死候选表（含 `0080`/`0082`/`0083` 涉及的候选表、审批记录与驳回记录表），候选管线随之移除；`0086_drop_word_submission_search.sql` 删除 FTS5 搜索表。

## 5. 额度与成本

| 限制                | 当前值                                                               |
| ------------------- | -------------------------------------------------------------------- |
| 授权数量            | 最多 100 个可见授权，含尚未删除的已撤销身份                          |
| Agent 每日 / 未处理 | 各自 1–1000，管理员设置；默认表单为 100 / 200                        |
| 全局每日投稿        | 1000 条，UTC 日；重复内容也计入，幂等重放不计                        |
| 全局未处理          | 5000 条；`pending/approved/reviewing/passed/rejected/failed` 计入    |
| 请求速率            | 每 IP 和每 Agent 各 30 次/分钟；不承诺全球严格一致的分布式计数       |
| 外部模型调用        | 无应用次数上限，仍与手动补词共用调用账本；数据库先记账再请求         |
| 外部瞎掰王检索      | 无应用次数上限；每次基础检索/提取最多 1 credit，仍按请求唯一编号记账 |

模型按分类分组：瞎掰王每组最多 1 条，其他游戏最多 5 条；投稿接口每批最多 30 条的上限不变。一个批次可能需要多次调用；部分组成功、后续失败时保留已有结果。失败和结果不确定的外部调用不退款，也不自动重试。人工发布不消耗模型。

外部手动审核不再使用原 454 次检索上限；模型调用额度已取消，只留调用记录。手动补词与外部审核共用调用账本，共享账本中的外部调用仍计入其已用量。供应商的实际配额和计费规则仍有效。词库面板的 Tavily 数量包含手动补词和外部证据请求。外部证据失败时不会用 Agent 链接或搜索摘要悄悄代替。

瞎掰王提取多个独立来源时，部分来源失败但仍有成功提取的原文，就只使用成功的原文继续审核；引用校验与发布门槛不变。来源全部提取失败时，仅该词记为 `evidence:extractionFailed`，工作流继续处理其他词；这类部分失败的审核动作最终记为 `failed`，已完成的词保留结果。供应商请求错误、模型错误、数据库错误等仍立即停止当前动作，不自动重放。来源级提取失败会记录工作流和词条编号、来源序号、成功数量及脱敏后的供应商错误，不记录原始链接、密钥或词条内容。

## 6. 存储、审计与上线

- `0076_agent_word_submissions.sql` 新建隔离区、凭证、每日账本、命令、审核事件和证据请求账本（FTS5 搜索表随 `0086` 删除，现不使用）；不重建原词表，不搬迁历史库存，没有现有数据的索引回填。
- 业务审核记录在 `word_submission_events`，随事务写入，可从词条详情查看最近 10 次命令中的最新 100 条事件。签发、换证、状态变化和收稿开关另在 `word_submission_control_events` 持久化；该控制面账本目前供运维 SQL 审计，未提供专用 UI。两个账本都不保存原始 Token。
- 用事务维护全局/Agent 数量，不按历史投稿全表扫描仪表盘。投稿流用标题/分类 LIKE 搜索，游标为 `createdAt|id`；候选、指纹、凭证、时间窗和审计读取使用对应索引。
- 真实迁移后的 D1 测试覆盖 100 / 10000 个带候选的历史批次（FTS5 时代的读预算：空前缀查询 <100 读行，命中查询 <150，30 批满页及下一页各 <1000；搜索已改 LIKE，读预算待重新计量）；单条写入 <150 写行，最大 30 条写入 <1000。读写预算包含事务和触发器，本地计量不等于生产账单。
- 单条资料提取失败会更新对应条目和审计。30 条均失败时，100 / 10000 个历史批次下的测试预算均为 <5000 读行、<3000 写行；实际生产用量需上线后观察。
- FTS 和状态索引引入持续写放大，换取后台检索与固定量分页。新表初始为空，无旧表复制成本；生产增长速度和真实 D1 计费必须上线后监控。第一版保留幂等和来源历史，没有后台自动删除/归档任务。
- 新增 `WORD_SUBMISSION_REVIEW` Workflow 与 `WORD_SUBMISSION_LIMITER` binding；无需新密钥，复用现有 Gemini/Tavily。
- 发布前先迁移 D1，再发布包含新 Workflow 导出的 Worker，最后发布 Web。回滚时先暂停外部收稿、等待正在运行的审核终止，再回退应用；不要删除来源、序列和已见历史，也不要为了回滚删除新表。

实施验证不包含生产迁移或真实付费模型调用；上线仍需核对 Workflow binding、已有 provider 密钥、生产额度和 D1 指标。
