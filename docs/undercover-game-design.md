# 谁是卧底游戏与 UI 设计

> 状态：主对局已实现并通过本地浏览器验收；自动供词仍待完成上线验收  
> 最后更新：2026-09-21  
> 展示名：谁是卧底  
> 游戏 ID：`undercover`，已注册引擎、Worker 和客户端模块  
> 关联文档：[房间界面契约](./room-shell-contract.md)、[多游戏平台架构](./multigame-platform-design.md)

## 1. 定位与决策边界

面向同桌聚会：玩家面对面描述、讨论、用手指投票；手机只负责发词、房主揭示出局者和自动判胜。用户不需要在线上重复线下操作。

### 1.1 用户已明确的要求

- 新增「谁是卧底」游戏，包含完整的页面、按钮和玩家互动设计。
- 支持白板，在房间设置中选择是否启用。
- 不做线上投票。线下决定出局者，由房主在手机上处理并揭示身份。
- 根据剩余身份自动判定平民、卧底或白板获胜。
- 支持房主接管的测试机器人，使一名真人可以独立测试完整对局；不做自主描述或调用 AI 的机器人。

### 1.2 本稿采用的推荐默认值

人数范围、卧底配比、白板具体胜利条件、词库规模等是前述讨论中的建议，并非用户逐项确认的规则。为使本稿可评审、可实现，以下统一采用一套明确默认值；实现前确认这些产品参数。

本稿取代此前线上投票方案，不保留投票面板、票数、投票提交进度、线上 PK、逐人发言确认、发言倒计时或「开始投票」按钮。平票和发言顺序完全在线下处理。

## 2. 玩家与规则

### 2.1 人数配置

| 配置     | 推荐规则                                    |
| -------- | ------------------------------------------- |
| 总人数   | 4–12 人，默认 8 人                          |
| 卧底人数 | 4–6 人：1 名；7–9 人：2 名；10–12 人：3 名  |
| 白板开关 | 默认关闭；开启要求至少 6 人                 |
| 白板人数 | 开启后固定 1 名，替换一名平民，不增加总人数 |
| 平民人数 | 总人数减去卧底与白板人数                    |

8 人示例：关闭白板为 6 平民、2 卧底；开启后为 5 平民、2 卧底、1 白板。首版不提供独立调整卧底人数或多白板选项。

### 2.2 身份与信息

| 身份 | 开局本人看到                 | 游戏目标                             |
| ---- | ---------------------------- | ------------------------------------ |
| 平民 | 平民词，不显示阵营名称       | 找出并淘汰全部非平民                 |
| 卧底 | 卧底词，不显示阵营名称或同伴 | 隐藏身份，达到人数优势条件           |
| 白板 | 「你是白板」「本局没有词语」 | 根据他人描述推测主题，存活到最后两人 |

平民和卧底各自拿到同一个阵营词，两个词相关但不同。玩家线下描述时不得直接说出自己的词。系统不录音、不识别违规，也不裁决描述质量。

未公开的阵营不能通过词卡颜色、座位边框、图标、提示音或辅助技术标签泄露。初始阵营配比公开；进行中只显示总存活人数，不额外展示实时剩余阵营人数。

### 2.3 揭示与胜负

**房主确认揭示身份即淘汰该玩家。** 没有「房主私下查看」「只揭示不淘汰」「撤销揭示」或「手动指定胜利方」功能。

每次成功揭示后，在同一次服务端状态提交中判胜：

| 条件                                     | 结果                                 |
| ---------------------------------------- | ------------------------------------ |
| 白板存活，且场上只剩 2 人                | 白板独赢，不与其他阵营共享胜利       |
| 白板存活，场上超过 2 人                  | 继续游戏，即使卧底人数已达到平民人数 |
| 无存活白板，且卧底全部出局               | 平民获胜                             |
| 无存活白板，且卧底人数大于或等于平民人数 | 卧底获胜                             |
| 其余情况                                 | 继续游戏                             |

关闭白板时直接使用后两条阵营判定；白板出局后亦如此。首版不加入白板出局猜词翻盘。

边界示例：

- 2 平民、1 卧底、1 白板：继续。
- 1 平民、1 卧底、1 白板：淘汰白板则卧底胜；淘汰另外任一人则白板胜。
- 2 平民、1 白板：淘汰白板则平民胜；淘汰平民则白板胜。
- 无白板，2 平民、1 卧底：继续；再淘汰一名平民则卧底胜。
- 1 平民、2 卧底、1 白板：继续；淘汰最后一名平民后仍继续，白板未出局且尚未剩两人。

## 3. 状态与完整流程

```text
等待入座
  -> 正在准备词语
  -> 查看词语 / 确认已记住
  -> 游戏进行中
       -> 房主揭示一名出局者
       -> 服务端判胜
            -> 未结束：继续线下游戏
            -> 已结束：最终结算
  -> 房主再来一局：返回等待区，保留座位与设置
```

- 等待区人数坐满且配置有效，房主才能开局；无需额外开局前准备按钮。
- 开始准备时固定本局名单和配置，禁止换座、补位或修改设置。
- 全员确认「已记住」后自动进入游戏，不需要房主再次开始。
- 房主不能代真人确认看词；可接管机器人逐席确认。真人与机器人中的白板同样需要确认。
- 游戏进行中不记录发言轮次；「第 N 次揭示」仅表示线上淘汰顺序，不冒充线下轮数。
- 揭示结果弹层是本地展示，不是必须等待全员关闭的全局阶段。
- 准备失败有显式失败状态；中止有独立终态，不伪装成正常结算或任何阵营获胜。

## 4. UI 视觉与布局

### 4.1 设计原则

- 使用现有主题、字体、间距、图标、头像、座位外观和房间外壳，不增加独立皮肤或游戏大厅。
- 主体采用共享房间的 `seats` 内容模式；不为本游戏复制邀请、资料、连接和房主管理界面。
- 所有阵营在揭示前保持中性视觉。揭示后可配合主题语义色，但必须同时提供身份文字。
- 主要命令用图标加中文文字；邀请、规则、记录和更多操作使用已有图标并提供可访问名称和桌面提示。
- 页面以状态栏、座位区、记录摘要和底部操作区组成，不把整个页面嵌套在多层卡片里。
- 布局沿用共享座位板的响应式规则，不为此游戏擅自改变其他游戏的列数和几何。

### 4.2 手机端：游戏进行中

以下为 8 人房间的示意，实际列数按共享布局和可用宽度决定。

```text
┌──────────────────────────────────┐
│ 返回  谁是卧底 · 房间号   邀请 更多 │
│ 游戏进行中              剩余 6 / 8 │
│                                  │
│  1号     2号     3号     4号       │
│  头像    头像    头像    头像      │
│  小明    小红    小陈    我        │
│                                  │
│  5号     6号     7号     8号       │
│  头像    头像    头像    头像      │
│  已出局  小李    已出局  房主      │
│  平民           卧底              │
│                                  │
│ 最近揭示：7号 小林 · 卧底   记录   │
│                                  │
│ [查看我的词卡]  [揭示出局者]       │
└──────────────────────────────────┘
```

普通玩家没有「揭示出局者」按钮；未参赛旁观者也没有词卡按钮。房主标记、本人标记与出局身份各占明确位置，不能互相覆盖。长昵称截断时，资料面板提供完整昵称。

机器人座位持续显示机器人标记；房主接管机器人时增加「正在接管 3 号 · 机器人」控制条，词卡按钮明确变成「查看 3 号词卡」，不能仍写「我的词卡」。详见第 5.6 节。

底部操作区固定在安全区上方；滚动内容预留其高度。窄屏时允许按钮布局换行，不缩小文字到不可读、不横向溢出。

### 4.3 桌面端

```text
共享房间头部、连接状态
---------------------------------------------------------
游戏进行中 · 剩余 6 / 8

                座位主区           | 揭示记录
       1号  2号  3号  4号          | 第1次：5号 平民
       5号  6号  7号  8号          | 第2次：7号 卧底
                                   |
---------------------------------------------------------
                  查看我的词卡      揭示出局者（房主）
```

有足够宽度才启用侧栏，否则记录回到弹层。保持主区最大宽度和座位尺寸约束，不把少量座位无限放大。

### 4.4 座位状态

| 状态         | 展示                                   | 点击行为                           |
| ------------ | -------------------------------------- | ---------------------------------- |
| 等待区空位   | 座位号、入座入口                       | 复用入座确认                       |
| 等待区已入座 | 头像、昵称、本人 / 房主标记            | 查看资料；本人可离座               |
| 看词阶段     | 增加「未确认 / 已记住」标记            | 仍是查看资料                       |
| 进行中存活   | 正常头像和昵称，不显示阵营             | 查看资料                           |
| 已出局       | 降低视觉强调，显示「已出局」和公开身份 | 查看资料，不可在揭示面板中再次选择 |
| 暂时离线     | 独立连接状态标记，不改变存活状态       | 查看资料                           |
| 正常结算     | 全部公开阵营，保留出局与存活区别       | 查看资料                           |

头像始终用于资料，不因房主身份变成危险的揭示入口。揭示选人使用独立面板。

## 5. 页面与按钮规格

### 5.1 等待区与房间设置

显示游戏名、人数进度、阵营配比；无整页玩法介绍。规则在专门的规则弹层内查看。

| 控件         | 行为                                                     |
| ------------ | -------------------------------------------------------- |
| 人数步进器   | 4–12 人；不能低于已入座人数，不自动移出玩家              |
| 启用白板开关 | 至少 6 人才可开启；不足时说明原因，不擅自增加人数        |
| 配比摘要     | 根据人数与白板开关实时显示                               |
| 词库类别菜单 | 默认全部；仅展示有启用词对的类别，具体类别以实际库存为准 |
| 保存设置     | 保存有效配置并向全员同步；取消不修改房间                 |
| 开始游戏     | 仅房主可见；人数不足等条件不满足时点击给出具体原因       |
| 邀请         | 复用房间链接 / 二维码；不包含词语或身份                  |

白板开启时人数不能降到 6 以下，提示先关闭白板，不静默关掉设置。进行中所有人可查看本局配置，但不能修改。首版不提供自定义词、难度切换或独立卧底人数调节。

### 5.2 准备与看词

准备中显示「正在准备词语」，不显示上一局词卡；失败显示具体原因及房主的「重试」「返回等待」操作。其他人看到当前准备状态，无重试管理按钮。

看词阶段顶部显示「已记住 5 / 8」，座位标记对应确认状态。

```text
我的词卡                         关闭
------------------------------------
          [遮挡的词语区域]
             按住查看
------------------------------------
              已记住
```

- 点击「查看我的词卡」打开遮挡式弹层，按住查看、松手隐藏；测试接管时改为对应机器人座位的词卡，保持相同遮挡交互。
- 键盘和辅助技术提供等价的「显示词语 / 隐藏词语」操作，避免只能长按。
- 白板揭开后显示「你是白板」「本局没有词语」。有词玩家不出现阵营名称。
- 玩家至少主动查看一次后才能确认「已记住」；本地记录仅用于交互，不作为防作弊机制。
- 确认按钮提交成功后变成「已记住」，自动遮挡；仍可再次查看词卡，不能反复取消就绪拖动阶段。
- 关闭弹层、失去页面可见性、切到后台或离开房间时隐藏内容；恢复页面不自动展开。
- 进入游戏后词卡只负责查看，不再出现确认按钮。出局玩家仍能查看自己的词，不会提前看到另一方词语。

### 5.3 房主揭示出局者

主按钮「揭示出局者」仅在进行中对当前房主显示，包括已经出局的房主。

1. 打开选人面板，列出全部本局玩家；存活玩家可选，出局者标记不可再揭示。
2. 每项显示座位号、头像、昵称和单选状态；未揭示身份和词语绝不进入选项说明。
3. 房主可以选择自己，也可以选择暂时离线但仍存活的玩家。
4. 选中前按钮为「选择出局者」；选中后为「揭示 5 号身份」。选择本身不发送淘汰命令。
5. 点击后弹出最终确认，取消返回选择面板并保留选择。

```text
确认揭示并淘汰？

5号 · 小明

身份将向全员公开，该玩家退出本局。
揭示后无法撤销。

           [取消]  [确认揭示]
```

「确认揭示」发送一次操作，展示提交中状态。结果不确定时显示「正在确认」，不能变成允许再次执行的新揭示。成功后关闭选择和确认面板，展示服务端结果；明确拒绝则保留上下文，显示原因。

### 5.4 揭示结果与记录

未结束时全员出现紧凑结果弹层：「5 号 · 小明」「平民」「已出局」，按钮为「知道了」。不出现词语，不提供「下一轮」按钮。

- 可用短暂淡入强调结果，不使用长动画阻挡线下游戏。
- 每人独立关闭，房主不必等待其他人关闭就能处理下一次线下结果。
- 多个结果到达时更新为最新结果，旧结果保留在记录中，不堆叠多层弹窗。
- 记录按揭示顺序列出序号、玩家与公开阵营；不包含票数、投票人或推测的线下轮数。
- 重连后恢复座位和完整记录，不逐条重播旧弹窗。
- 若本次揭示已判胜，直接进入结算，不再先阻挡在淘汰弹层。

### 5.5 最终结算与再来一局

```text
                 平民获胜
           所有卧底与白板均已出局

       平民词：豆浆    卧底词：牛奶

        [身份揭晓]   [出局记录]
       1号 小明 · 平民 · 存活
       2号 小红 · 卧底 · 第2次出局
       ……

             [再来一局]（房主）
```

结算文案根据实际模式生成，例如无白板时不写「白板均已出局」。展示两个词、所有人的阵营、存活状态和揭示顺序。白板没有词，不用空字符串或平民词冒充。

「再来一局」由房主操作，返回等待区并保留座位和配置；不立即跳过看词阶段。新一局重新抽词、分配身份、清空确认与揭示记录。结算不发放本稿未定义的积分、抽奖或成长奖励。

### 5.6 机器人与单人流程

与其他游戏一致，房主可以直接添加和接管机器人，无需独立模式开关。一名真人房主可以配合多个机器人走通发词、看词确认、揭示和判胜。机器人是由房主操作的座位，不自动描述、不投票、不调用模型，也不自动确认看词。添加机器人不改变人数限制、阵营配比或胜负规则。

#### 等待区设置

- 房主先本人入座，再点击「填满机器人」，只填充空位，不替换真人；已满时给出「座位已满」反馈。
- 机器人统一显示机器人标记、座位号和名称，例如「机器人 3 号」，不伪装成在线真人。
- 「清除机器人」仅在等待区可用，只移除机器人，保留真人。
- 开局后禁止新增、移除或替换机器人；无法继续时按正常流程中止。
- 房间可有其他真人加入，但房主只能接管机器人，真人依然自行查看与确认。

#### 接管 UI 与操作

复用共享座位接管和控制条能力；点机器人头像仍先打开资料面板，面板提供「接管此机器人」。已有长按快捷入口可保留，但不能作为唯一入口，键盘与触控都必须可达。

```text
游戏进行中                       剩余 8 / 8
正在接管 3号 · 机器人            [返回本人]

                 共享座位区

[切换接管] [查看 3号词卡] [已记住]（看词阶段）
[切换接管] [查看 3号词卡] [揭示出局者]（进行中）
```

- 「切换接管」打开机器人单选菜单，显示各机器人的看词确认和出局状态；不在列表中批量展示词语或未公开阵营。
- 接管后，词卡与「已记住」只作用于选中机器人。词卡标题明确写「3 号 · 机器人词卡」，有词机器人仍不标平民或卧底，白板正常显示白板词卡。
- 房主需逐席查看并确认，不增加「全部已记住」绕过确认流程。最后一个参赛座位确认后，仍由服务端自动进入进行中。
- 接管期间「揭示出局者」「中止本局」等管理命令仍以真实房主身份执行，不以机器人身份冒充房主；揭示选人依旧需要二次确认。
- 「返回本人」清除接管目标；切换目标或返回本人时立即关闭并遮挡上一张词卡，清除旧确认草稿，不能短暂显示前一座位的词。
- 出局机器人仍可接管查看其自己的词卡，与真人出局后的规则一致；不能因此看到所有阵营或修改既有揭示结果。
- 房主本人出局不影响接管或管理。房主转让后，旧房主立即失去接管权限，关闭机器人词卡；新房主从本人视角开始，可重新选择机器人。
- 刷新、重连后从本人视角恢复，机器人已经确认和出局的状态保留；结算、中止及再来一局均清除本地接管目标。
- 手机端空间不足时控制条和底部操作分行排列，不挤压词卡与危险操作按钮。

#### 单人测试路径

1. 创建房间，本人入座；需要测试白板时开启白板设置。
2. 点击「填满机器人」，人数满足配置后开始游戏。
3. 本人查看词卡并确认，再依次接管机器人，查看词卡并确认，全员完成后进入进行中。
4. 按要测试的路径由房主逐个揭示出局者，检查公开记录、存活人数和自动判胜。
5. 结算后「再来一局」，保留机器人座位和配置，重新抽词及分配身份。

含机器人的房间使用同一规则引擎、已审核词库和发词去重契约，不触发额外模型生成或绕过库存限制。单人流程能走通完整对局，但随机分配不保证每局覆盖所有胜负分支；各胜负边界仍用确定性测试验证，不额外提供手动改身份或指定胜利方的入口。

## 6. 权限与玩家互动

下表描述真人权限；第 5.6 节定义机器人接管权限，不开放真人接管或私下查看其他人的未公开阵营。

| 能力                | 存活参赛者 | 出局参赛者 | 未参赛旁观者 | 当前房主                   |
| ------------------- | ---------- | ---------- | ------------ | -------------------------- |
| 查看自己的词卡      | 可以       | 可以       | 不可以       | 仅本人参赛时可以           |
| 查看公开记录与资料  | 可以       | 可以       | 可以         | 可以                       |
| 查看其他未公开身份  | 不可以     | 不可以     | 不可以       | 不可以                     |
| 揭示出局者          | 不可以     | 不可以     | 不可以       | 进行中可以，自己出局不影响 |
| 修改配置 / 开始游戏 | 不可以     | 不可以     | 不可以       | 仅等待区可以               |
| 中止本局 / 再来一局 | 不可以     | 不可以     | 不可以       | 对应阶段可以               |

房主列表示附加管理能力，不额外授予真人私密信息。房主可查看所接管机器人的词卡并代其确认，不能查看其他真人词卡。所有管理命令及机器人代理操作由服务端校验当前房主、阶段与目标机器人，不能仅靠隐藏按钮控制。

- 进行中加入者只能旁观，等待下一局才可入座。
- 出局玩家不再参与正式描述或线下投票；由同桌遵守，应用不假装可以约束口头行为。
- 不提供游戏内聊天、举报投票或在线举手。线下平票、重述和讨论无需任何线上状态改变。
- 房主在等待区可直接填充机器人，看词与进行中可接管机器人；具体入口与限制见第 5.6 节。
- 转让房主复用平台已有能力；只改变管理权限，不改变角色、座位、存活状态或词卡权限。

## 7. 中止、断线与错误状态

| 场景                      | 产品行为                                                               |
| ------------------------- | ---------------------------------------------------------------------- |
| 点击尚不可用的操作        | 保持视觉状态并给出具体原因，例如「还差 2 人入座」；不是无反馈点击      |
| 玩家断线 / 退出页面       | 不自动出局，不清除词语、确认或座位；重连恢复本局                       |
| 网络恢复中                | 显示共享连接状态；新危险操作不发送，点击说明正在恢复连接               |
| 揭示已提交但响应丢失      | 使用现有命令恢复确认结果；不重新生成淘汰操作、不重复揭示               |
| 选人后房主发生转让        | 原房主提交被拒绝，关闭失效管理入口，按最新权限更新                     |
| 目标已被揭示 / 对局已结束 | 服务端拒绝过期动作并同步最新状态，不能淘汰下一局同座位玩家             |
| 房主断线                  | 不自动乱选出局者；按平台现有房主管理恢复或转让流程处理，不另建争抢机制 |
| 真人长期缺席、无法继续    | 房主可中止；不代真人确认词卡，也不凭超时淘汰；机器人按测试接管流程操作 |
| 选错但尚未确认            | 取消或更换目标                                                         |
| 已确认揭示错误            | 不撤销已泄露的信息；需要重来时中止本局                                 |

「中止本局」放在更多菜单，不放在主操作旁。准备、看词、进行中均可由房主中止，需确认「本局将结束，不计胜负」。中止后展示中止状态和公开记录，不继续开放词卡、不自动公开尚未揭示的身份或双方词语；房主可返回等待区。已发出的词对仍视为使用过。

业务拒绝显示具体中文原因；未知错误提供反馈和明确重试入口。日志不包含秘密词语或完整身份表。错误恢复不能用清空整局、重新随机身份或偷偷换词处理。

## 8. 词库与发词

### 8.1 内容要求

- 内容单位是词对，不能从两个独立词随机拼接。
- 首批推荐目标约 200 对，通过自动审核后按上线验收要求抽样人工复核和试玩；日常补库不要求逐对人工批准。目标数量不代表已有可用库存。
- 同类、双方常见程度接近、有共同描述空间且存在可描述差异；避免冷僻知识、同义词或完全无关词。
- 「豆浆 / 牛奶」「电梯 / 扶梯」仅为设计示例，不视为已完成试玩验收。
- 词对记录稳定标识、两词、类别、审核和启用状态。只有审核启用的词对能发出。
- 两词随机分配给平民和卧底前，必须确认双向可玩；本局分配结果持久化，重连不重新随机。

### 8.2 供词与去重

首版用预先审核的库存，不在开局时调用 AI，不提供参赛房主自定义词。房主也是玩家，不能提前看见两个词。

- 同一房间优先排除已用词对，调换双方词语仍算同一个词对。
- 不承诺跨账号、跨房间永不重复，也不沿用其他游戏的特殊供题进度规则。
- 类别库存耗尽时明确显示「该类别的新词已用完」，房主可返回设置换类别，或确认「允许本局使用旧词」。
- 允许重复仅授权该次准备任务，不悄悄成为永久设置；重试保留同一次明确授权。
- 全部启用库存为空时不能靠重复解决，显示「暂无可用词语」并允许返回等待。
- 一次准备任务最多成功分配一组词和身份；失败重试回放已提交结果，不换词或重复消耗记录。
- 已固定的题包不因之后库存停用而改变，确保进行中的对局能够完成。

### 8.3 词对分类与选择 UI

词语不限于物品名，也允许人物身份、动作、生活场景及容易理解的短语。分类服务于玩家选题，不应把内容限制为日常物品清单；熟悉的题材同样可以通过有趣的相似点和差异产生讨论。

分类属于整个词对，不分别给平民词和卧底词分类。每个词对只有一个主分类，可附多个生成与审核标签，例如「动作」「反差」「怀旧」「网络用语」。标签不重复生成库存条目，不作为首版额外设置。

| 首版推荐分类 | 内容范围                                           |
| ------------ | -------------------------------------------------- |
| 美食饮品     | 食物、饮料、烹饪及用餐习惯                         |
| 日常生活     | 日用品、家居、购物及日常习惯                       |
| 校园青春     | 课程、考试、社团及校园经历                         |
| 职场打工     | 职业、工作情境、办公活动及职场用语                 |
| 社交关系     | 常见人际身份、交往方式及社交行为                   |
| 动作状态     | 动作、情绪和生活状态，例如赖床与熬夜这类可描述概念 |
| 影视文娱     | 大众作品、角色、音乐、节目及娱乐活动               |
| 运动游戏     | 运动项目、电子游戏和线下游戏中的常见概念           |
| 出行场景     | 交通、旅行、公共场所及外出经历                     |
| 自然万物     | 常见动物、植物、天气和自然现象                     |

以上是推荐分类，不代表已有合格库存。品牌、作品角色或网络用语不一刀切禁止，但必须通过熟悉度、时效性和双向可玩审核，不能靠冷门知识或牵强玩梗凑题。不复制商业题库、作品台词或长篇受保护内容。分类有重叠时按主要共同主题选一个；模型不能自行新增分类。

- 房间设置使用单选菜单，默认「全部」，按上表展示有库存的分类；首版不做多选。
- 「全部」是筛选选项，不是词对的存储分类；从所有类别的合格、符合本局去重条件的词对中抽取。
- 选定单类时只从该类别抽取，不能缺词后静默切换到其他类别。
- 菜单仅展示有启用库存的类别；类别有库存但本房间已全部用过时，按第 8.2 节处理。
- 等待区和本局配置摘要显示所选范围，例如「词库：饮食」；进行中锁定设置。
- 选择「全部」时，结束前不额外公开实际抽中词对的类别，避免给白板增加题目提示；结算可显示实际类别。
- 分类菜单不展示词对预览或示例答案，避免参赛房主提前见题。
- 去重基于词对本身，切换分类或「全部」不能重置房间的使用记录。

### 8.4 后台自动生成、审核与入库

首版包含后台自动供词，而不是一次性人工词库。采用「定时检查库存 -> 按分类缺口生成候选 -> 程序校验去重 -> 独立模型审核 -> 自动入库」，玩家开局只读取已启用库存。后台自动生成与开局不调用 AI 是两个不同要求。

参考[瞎掰王自动供题](./fibking-word-supply.md)的调度、持久化候选、独立审核、预算和失败终态思路，但不照搬其冷僻词释义标准、账号进度或搜索取证流程。谁是卧底追求常见、易描述、有反差的词对，不把词义陌生当优点。

- 日常定时检查各类别启用数量、新增消耗和待复审数量，在预算内优先处理库存不足、类别偏少及过度重复的主题。
- 先消费已有待审候选，再生成新候选；批次允许零产出，不能为凑数量放宽规则。
- 生成和审核使用分开的请求、提示词及记录；审核者重新检查共性、区别、熟悉度、分类和双向可玩性，不直接采信生成者自评。独立请求不保证模型判断正确。
- 审核通过且预算允许的新词对自动发布，无须逐对人工点击通过。失败、被拒绝、待审、已发布必须有明确记录。
- 日常词对直接生成；涉及作品、人物、热梗的关键事实或时效性有疑问时需检索核实，无法核实则不发布，不为所有普通词对强制增加搜索成本。
- 常见词也可以好玩，审核不能用「不是新奇词」直接淘汰；重点看是否有自然的共同描述、可辨别差异和讨论空间。

生成 prompt 模板：

```text
你在为中文同桌聚会游戏「谁是卧底」设计词对。

按本次请求提供的分类、主题、缺口和已有词对，生成最多 30 组候选。
允许物品、人物身份、动作、场景以及大众熟悉的短语，不要只生成物品。
每组两个词，分别发给平民和卧底；有词玩家不知道自己的阵营。
游戏还可能包含一名没有词语、只能听其他人描述的白板玩家。

要求：
1. 普通中文玩家无需解释就认识两个词。
2. 两词属于相近类别，至少有两个自然的共同描述角度。
3. 至少有两个清晰区别，便于玩家通过多次描述发现身份差异。
4. 不接受同义词、别名、地区叫法或一方包含另一方的词对。
5. 两词熟悉程度接近，交换平民词和卧底词后仍可玩。
6. 品牌、作品角色及网络用语需大众熟悉；避免冷门知识、歧视性刻板印象。
7. 不通过只更换颜色、大小等修饰词凑数量。
8. 每组仅从请求提供的分类表选一个主分类，可附内容标签；不得自创分类。
9. 排除本批重复、交换顺序后的重复和随请求提供的已有词对。
10. 不确定的候选直接舍弃，不必凑满。

输出 JSON 数组，每项包含：
- 词语甲
- 词语乙
- 分类
- 共同描述角度：至少两项
- 区分特征：至少两项
- 潜在问题：歧义、难度失衡或容易泄底的风险

不要把生成结果标记为已经审核、试玩通过或可以直接发布。
```

正式生成请求附带分类表、主题方向以及有长度上限的相关历史样本，不随库存增长无限塞入完整词库。程序仍对全库独立去重，不能相信模型已经排除重复。示例输出字段用于说明审核材料，实施时按仓库命名约定定义结构化契约。

| 步骤     | 必须产出的证据                                                                   |
| -------- | -------------------------------------------------------------------------------- |
| 生成候选 | 真实输出、主题、模型及 prompt 版本；失败不能冒充零候选成功                       |
| 程序校验 | 结构、空词、两词相同、非法分类，以及跨分类、跨批次和交换顺序后的重复检查结果     |
| 独立审核 | 各项质量判断及理由、审核版本；不确定或不合格的候选不能直接发布                   |
| 自动发布 | 通过记录、启用时间、稳定词对标识；原子入库，重试不重复发布或计数                 |
| 人工抽查 | 样本接受与拒绝原因、误放与误拒情况；与模型审核结果分别记录                       |
| 试玩抽样 | 记录过早暴露、难以区分、交换后失衡和白板参与情况，不假装所有自动入库词都经过试玩 |

共同描述角度、区分特征和风险只用于审核，不发给玩家作提示。程序能发现结构和重复问题，不能代替人判断词对是否有趣、平衡或适合白板。

### 8.5 自动补充与旧词替换

- 补充：按分类缺口和使用量追加新词对，不能因为总量达标就长期让某些类别没有新题。库存目标和每日、每月调用上限在实现前根据真实产出与可用额度确定，不能直接给新游戏复制一份瞎掰王额度。
- 更新：审核标准变化、内容过时或抽查发现问题时，将相关旧词对加入复审队列。确认为不合格才停用；外部服务超时不等于词语质量不合格，未完成复审不能批量清空库存。
- 替换：停用的不合格词由后续通过审核的新词补足。更换任一词语即视为新词对，不覆盖原标识；只修订分类或审核材料则保留原标识和使用历史。
- 历史：停用只影响后续抽取，不能删除正在进行的题包、改写已发词语、重置房间去重或导致旧房间无法继续。
- 新鲜度：不因「使用过」或「发布时间旧」直接删掉好词；通过补新和房间去重提高新鲜度。账号级跨房间去重仍不在首版承诺范围。
- 去重：同一词对重新审核启用不是新增；交换词序、修改分类或改标签不能刷新增数量。生成时降低反复使用相同单词、相同区别模式的倾向。
- 限额：生成、审核、必要检索及复审统一受请求账本和预算控制。共用供应商项目时必须核算与瞎掰王的合计消耗，不能自动升级付费或挤占现有预算。
- 恢复：任务和外部请求领取状态持久化；同一操作响应不明不盲目重发、不退还额度。失败有可观察终态，后续调度处理未消费任务，不无限自动重试。
- 供词故障：停止失败批次，现有合格库存继续供游戏使用；库存耗尽按第 8.2 节处理，不能转为开局现场生成或偷偷抽取被拒绝词。

### 8.6 自动化上线验收

首批先真实生成约 60 对候选，核对去重、独立审核与自动入库链路，人工抽查各类实际输出并试玩部分词对。保留不进入提示词的评测样本，检查误放与误拒后再开启日常自动发布；不要求日后每个词对都先人工试玩。

分别报告生成量、去重后数量、模型通过量、实际发布量、人工确认量、试玩量、各类库存与请求消耗。约 200 对是初始库存目标而不是永久容量上限，也不是产量保证。自动审核通过不能被表述为人工认可或已经证明好玩；单元测试和调度成功不能代替真实内容验收。

当前尚未运行真实模型、审核、试玩或自动补库；本节定义首版后台自动化范围，不授权模型调用、费用支出或生产发布。具体模型、调度频率、预算、水位和共享基础设施在实施前核对现有代码与供应商配额后确定。

## 9. 技术接入与状态约束

### 9.1 所有权

现有源码已存在纯引擎、Worker、客户端三个游戏 catalog，以及共享房间 `seats` 内容契约。本游戏在这三个运行环境中注册独立模块，不能将规则塞入共享房间或复制另一游戏模块。

| 层       | 本游戏职责                                                         |
| -------- | ------------------------------------------------------------------ |
| 纯引擎   | 配置校验、名单冻结、看词确认、揭示淘汰、胜负、中止与重开规则       |
| Worker   | 认证、供词与准备恢复、调用引擎、持久化与广播；复用平台命令处理管线 |
| 客户端   | 配置、词卡、揭示选人和确认、记录、结算；基于权威状态生成按钮与权限 |
| 共享平台 | 房间、连接与命令恢复、座位、资料、邀请、房主管理；不判断本游戏阵营 |

相关现有入口：

- [纯引擎 catalog](../packages/game-engine/src/games/catalog.ts)
- [Worker catalog](../packages/api-worker/src/games/catalog.ts)
- [客户端 catalog](../src/games/catalog.ts)
- [RoomShell 模型](../src/features/room/model/RoomShellModel.ts)

这些是已核对的接入锚点，不是完整实施文件清单；具体类型扩展、存储和路由需在实现阶段双向核对调用方与消费者。本稿不宣称接入无需修改任何平台类型。

### 9.2 必须持久化的信息

保存本局标识、配置快照、固定参与者、准备任务状态、词对及阵营分配、玩家看词确认、出局状态、按序揭示记录、胜者或中止结果。字段命名沿用仓库概念，实施时逐个检索确认。

不持久化虚构的线上票数、发言顺序或讨论阶段；本地弹层开关、词卡是否展开和选人草稿也不进入权威游戏状态。

### 9.3 必须成立的不变量

1. 服务端是唯一权威；客户端不能自行扣减人数、提前显示身份或计算最终胜负。
2. 揭示一次性校验当前房主、当前对局、进行中阶段及目标存活状态，再原子提交出局、记录和胜负。
3. 被拒绝的操作不改变状态；同一已接受操作的恢复不产生第二条揭示记录。
4. 先持久化再广播，应用退出、重连和服务重启不能重新抽词或分配身份。
5. 名单冻结后不能通过离座、踢人或替换座位改变参赛者；普通房间退出不等于游戏淘汰。
6. 正常结束后不能继续揭示；中止不计胜负；新对局拒绝上一局未完成的旧操作。
7. 不建立另一份客户端或 D1 对局真相；词库和准备任务存储不能成为并行游戏状态。
8. 沿用面对面信任模型，UI 过滤和遮挡不等于服务端私密快照隔离，不宣称具有防作弊能力。
9. 仅支持当前客户端协议，但升级必须迁移并保留已有房间状态；不能因版本变化废弃本游戏或其他游戏的旧房间。
10. 参与者类型和机器人身份随权威房间状态保存；接管目标只属于客户端操作视角，不改变用户真实身份。服务端只允许当前房主代理机器人确认，拒绝代理真人；管理命令始终校验真实调用者。
11. 状态 v1 升级到 v2 时移除 `config.isTestMode`，保留原阶段、名单、词语、确认记录、出局顺序、胜者和已用词历史；持久化命令回执同步迁移，不接纳旧版客户端配置。

## 10. 无障碍与 UI 验收

- 所有按钮有中文可访问名称；选人面板提供单选语义和已选状态，出局身份不能仅用颜色表达。
- 触控目标至少 44 × 44；长昵称、长词和系统大字体不覆盖相邻信息，词语可换行且不得省略关键字。
- 弹层正确管理焦点，关闭后回到触发入口；确认揭示的危险动作不能获得意外的默认确认。
- 键盘可操作词卡、选人、取消和确认；隐藏词语时从可访问文本中同时移除词语。
- 减少动态效果设置下取消揭示动画；不依赖音效完成操作，首版不新增游戏专属提示音。
- 手机、窄屏、大屏桌面都验证底部安全区、滚动、弹层高度、记录可达性和无横向溢出。
