# 房间手牌与信息区：设计与实施方案

状态：实施中，九款游戏已接入共享房间手牌；原型已由 [PR #482](https://github.com/olveryu/WerewolfGameJudge/pull/482) 合入，第 2–4 步在 [Draft PR #487](https://github.com/olveryu/WerewolfGameJudge/pull/487) 按步提交，完整浏览器验收尚未完成。早期原型仅演示交互，不是功能清单。

本文件保留此前的迁移方案和验收背景，其中旧待办、颜色、手牌接口和终局规则已被新的决定取代。当前共享接口与外壳约束以[房间外壳契约](room-shell-contract.md)和现行代码为准；本文件中标为旧接口的内容不是实现依据，也不是已完成的声明。

实施过渡：四款舞台游戏的准备阶段已显式声明主持开始待办，阻塞时仍提示；终局复盘不标待办。五款身份游戏的分配角色、首次查看身份与查看后的开始游戏已声明；狼人杀黑死病不显示开始游戏，警长报名结束、发言结束和未投票的玩家投票入口已声明，报名、取消报名和退水加入确认，旧的主持确认候选名单阶段已移除。谁是卧底的出局选人已声明待办；准备失败时谁是卧底和瞎掰王仅在主持入口标记互斥决策。五款身份游戏的终局复盘完成状态按本人和对局保存；狼人杀终局先标昨夜信息，再标有效授权，最后提示本人复盘。共享层不再根据任务可用性推断待办，阶段行为仍须逐项验收。

狼人杀播报期间隐藏整个手牌（包括已打开的主持手牌），保留状态信息；播报结束后恢复玩家手牌，不自动重开主持手牌。阿瓦隆保持原有播报并行确认行为。

九款游戏的统一重开入口已接入带对局身份和终局边界校验的返回准备命令，被替代的旧公开命令已清理；词语游戏保留已用词记录。谁是卧底词库耗尽时，允许重复词对的确认使用新回合身份直接重新准备，不再借用旧的返回大厅命令。身份游戏终局重开按房主本人待办提醒；九款游戏的完整浏览器验收仍未完成。

### 已确认但尚未交付的重点

- **复盘与狼人杀终局**：狼人杀主持牌按「昨夜信息 → 授权 → 本局复盘」限制操作；昨夜信息确认和五款身份游戏的终局复盘完成状态保存在房间状态，刷新或重新入房后保持，重开后清除。未获授权的玩家保留阻塞待办；白天查看不替代终局查看。仍须完成浏览器验收。
- **角色行动子手牌**：狼人杀多个夜间行动选项已归入共享子手牌，入口按行动状态标待办；单一夜间行动直接显示，选座确认和取消不重复标记。在任何子手牌点操作牌立即回到主手牌，选座结束后停在主手牌；角色行动提交前保留确认，选座弹窗列出目标；取消不提交，状态失效后不能提交旧选择。其他游戏的行动待办仍需逐阶段核对，浏览器验收尚未完成。
- **身份游戏统一重开**：五款身份游戏已实现清局回准备、保留座位配置及对应确认，瞎掰王保留重新抽词；局中无需先看记录，终局只提醒房主自己的未完成事项。仍须完成浏览器验收。
- **完整阶段待办**：其余局中和终局事项、查询类别及机器人代打需逐游戏对照真实规则验收。阿瓦隆、秘密希特勒的未完成个人行动已声明待办，修改已提交投票或出牌不重复提示；瞎掰王进行中以大聪明选人作为待办，公布答案为可选操作。
- **验收边界**：按[效果说明的验收清单](room-hand-and-information-design.md#已确认规则的验收清单)检查九款游戏；固定信息区在极端屏幕空间不足时的处理尚未定案，需要先看实际效果。上述设计目标和旧方案中的条目均不代表已通过逐阶段验收。

## 1. 目标与边界

- 九款游戏统一房间的信息层级、操作入口和返回路径。**该出现的按钮逐项补齐，不是所有按钮都同时出现。** 游戏阶段、角色、权限、语音锁定、工作流和提交规则沿用真实代码，不从 mock 或其他游戏推断。
- 保留引擎规则、服务端协议、结算、奖励、投票权限和现有公开范围。不借此次迁移新增白天或出局技能。狼人夜间选座以包含 [#481](https://github.com/olveryu/WerewolfGameJudge/pull/481) 的主线实现为准。
- 玩法、笔记和建议编辑原有全页保留 URL、入口契约、布局、返回、刷新行为和功能；**只有房间手牌改用弹窗**。原型中简化的文本框、规则文案、绘画与揭晓样例都不进入正式版。

## 2. 房间布局与入口

| 场景                       | 信息区                                               | 行动区                                                                       |
| -------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| 开局前（含已发牌、未开始） | 紧凑显示公开配置，点角色看说明；不显示玩家的实际身份 | 当前玩家行动、手册、房主管理；狼人杀发牌前另有建议入口，不重复加「本局配置」 |
| 进行中                     | 公共阶段、进度及适用的公开记录；不重复铺开配置       | 当前主次行动同排；本局配置、手册、适用的房主管理                             |
| 选座中                     | 保留座位、目标提示与就近反馈                         | 取消与适用的确认操作以手牌呈现；沿用各游戏原有选座和提交规则                 |
| 专属游戏界面／逐段揭晓     | 原画布、编辑器、实时牌桌或作品视图保持挂载           | 右上角「菜单」对所有玩家可见；不常驻手牌                                     |
| 结束／中止                 | 结果、允许查看的记录或已收录作品                     | 回到底部手牌，不重复显示进行中的菜单；中止不等于正常结算                     |

**手牌布局。** 主次行动同排，牌身可以沉到房间下沿，牌名、图标与可点区域不能被遮住。手册、房主管理和菜单在原位置替换牌组，最左边是返回牌，不再加控制条。键盘聚焦与鼠标悬停可以突出牌面，但触屏单击直接执行，不要求展开或横拖。验收同时用女巫兼房主七牌实例、实际最多牌的场景和最长真实牌名；用仓库主题 token，不通过缩小字号或触区兜底。房主管理牌顶部用「待办」标签提示**可执行的待办**，不把整个房主管理菜单当作待办；原型里的两版提示不再作为准则。

| 入口                                 | 正式承载与复用                                                                                                                                                                                                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **玩法、攻略**                       | 手册子手牌 → 居中阅读弹窗。共享现有指南正文、适用范围和权限；保留原指南页面。没有攻略内容的场景不造空入口。                                                                                                                                                                                      |
| **笔记**                             | 狼人杀白天、结束时从手册进入。保留逐座记录、身份和上警标记、自由／投票记录、清除及现有条件允许的 AI 分析；两个阶段都能编辑且自动保存。旧页与弹窗用同一个房间／用户笔记存储。                                                                                                                     |
| **提建议／修改建议**                 | 发牌前主手牌。打开原板型编辑能力，保留预设、角色选择、编组校验等实际功能；底部固定提交。有未提交修改时，关闭前确认放弃。编辑中发牌：弹窗和草稿保留、提交禁用并解释。                                                                                                                             |
| **查看建议**                         | 发牌前有建议才在主手牌显示，复用现有列表、角色预览、点赞、自行撤回、房主采纳。列表打开期间发牌不抢关窗口；显示建议已结束并停用修改操作，不将旧列表伪装成实时可操作数据。                                                                                                                         |
| **本局配置**                         | 只读弹窗。与开局前的信息区共用同一公开配置内容：模式信息和角色构成，不复制布局、数据或规则。**点角色沿用现有角色详情弹窗**，不采用同窗切换。关闭角色详情回到刚才的角色入口及滚动位置。建议和房主改配置不随配置内容带进去。                                                                       |
| **身份、复盘、公开记录**             | 保留对应查看弹窗、权限和必要确认。公开记录入口靠近所属局势，不占手牌；秘密行动、私人身份和词语不能混入公共视图。                                                                                                                                                                                 |
| **房主修改配置、音乐设置、个人设置** | 房主操作归房主管理子手牌；音乐设置仅在开局前（含已发牌、未开始）出现，个人设置增加手牌入口。三项设置在房间内打开弹窗，原有独立页面保留；房间状态或权限变化时保留配置草稿并阻止提交。试听与游戏播放共用播放器但由各自的所有权管理，游戏播放优先。中止、再来一局、返回大厅等保留各自的确认和限制。 |

三种大弹窗仍要**看起来是弹窗**：房间留在原位并被遮罩压暗，居中且四周可见留边，右上角有明确关闭按钮。标题、必要页脚固定，中间独立滚动；手机软键盘打开后当前输入必须可见。关闭只退出最上层；不卸载房间或清除原有游戏输入。

## 3. 怎么实现

### 3.1 动作清单与共享接点

从最新 `origin/main` 建立生产清单：按各游戏真实屏幕、房间 hook、动作工厂、现有测试和路由对照。每行记录 `游戏 / 阶段 / 观众或权限 / 动作 ID / 显示与禁用条件 / 原入口 / 新入口 / 确认与提交 / 验收测试`。要同时检查共享更多操作、房主管理、阶段 HUD、配置区原按钮和独立页；每个入口标记「迁移／保留」及理由。优先记录已知的狼人杀跳过、改票撤回、非座位玩家可用动作、房主有无待办、音频锁定。未核实的动作不以示例补齐。

- **游戏层决定能力。** 游戏模块继续提供阶段、权限、动作、公开数据和具体弹窗内容，使用稳定动作 ID；共享层不按游戏 ID、按钮文字或 mock 阶段分支。[createRoomShellModel](../packages/web/src/features/room/model/createRoomShellModel.ts) 维持观众和房主模型约束；继续使用现有权限、音频锁定和提交管道，不在渲染层重复判断。
- **共享房间负责呈现。** 游戏适配器把现有能力投影为 [RoomPlayerActions](../packages/web/src/features/room/model/RoomPlayerActions.ts)、[RoomHostManagementModel](../packages/web/src/features/room/model/RoomHostManagement.ts) 和目录数据；`createRoomShellModel` 校验所有权与引用。共享 [RoomActionHand](../packages/web/src/features/room/components/RoomActionHand.tsx) 按最新模型构建主牌、子牌、主持牌和舞台菜单，「返回」仅是 UI 行为，不是游戏命令。旧焦点动作／更多面板已从动作渲染路径移除，[RoomBottomActionPanel](../packages/web/src/features/room/components/RoomBottomActionPanel.tsx) 只保留外壳容器职责；房主命令不会混为玩家动作。
- **信息与阶段视图。** [RoomGameSummary](../packages/web/src/features/room/components/RoomGameSummary.tsx) 保留开局前配置展示；局中及结束由 [RoomActionStatus](../packages/web/src/features/room/components/RoomActionStatus.tsx) 与已有信息区呈现状态。专属舞台保留 `RoomStageHud` 和游戏控制子树，通过显式 `actionSurface: 'menu'` 提供共享菜单，切换菜单不重挂作品或游戏控制。复盘入口仍由现有 review contribution 和 `useRoomReview` 提供。
- **避免永久双轨。** 同一场景只显示一个正式入口。迁完一组时同步更新受影响的契约和测试；旧路由不是旧房间工具栏，两者分别处理。无入口对应、缺处理器、重复动作 ID 等接线错误用类型和模型组装校验及早暴露，不做静默回退。

### 3.2 页面与弹窗只换外壳

优先复用现有 Ark UI 的 [RoomDialog](../packages/web/src/features/room/components/RoomDialog.tsx) 和仓库的确认队列。现有 `RoomDialog` 已有固定头尾和滚动体，遮罩点击不关闭（`closeOnInteractOutside={false}`），下层弹窗移除带来的连带关闭由共享的 `AppDialog.Root` 统一拦截；需为本次接入明确关闭语义（×、Escape／受支持的返回手势、遮罩不误关、脏稿拦截），**不得顺手改变已有复盘等调用者的关闭行为**。不引入第二套弹窗库或手写焦点陷阱。

| 内容     | 现有接点与改造                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本局配置 | 重用 [BoardInfoContent](../packages/web/src/features/room/components/BoardInfoContent.tsx) 及各游戏现有公开配置投影。若模式信息目前在外壳里，仅提取确实共享的数据与内容；两处连同模式信息一起消费同一投影。配置弹窗传 `footer={null}`，使用游戏现有 `onRolePress`，叠层复用原角色详情（共享实现见 [RoleCardDialog](../packages/web/src/features/room/components/RoleCard.tsx)），不另做新版角色卡，也不换成分栏。                                                                                                             |

| 建议编辑 | [ConfigScreen](../packages/web/src/games/werewolf/screens/ConfigScreen/ConfigScreen.tsx) 的 nominate 模式提交 `werewolf.board.nominate`；共用角色编辑器、草稿、校验和提交，不共用强制返回的外壳策略。[useConfigScreenState](../packages/web/src/games/werewolf/screens/ConfigScreen/useConfigScreenState.ts) 当前在发牌后返回房间：保留旧页行为，弹窗收到相同生命周期变化则转入不可提交状态。脏稿按真实编辑差异判断；关闭确认仅用于未提交修改。提交时重新校验最新权限，发牌竞争以服务器结果为准，失败保留草稿且不假装已提交。 |
| 建议列表 | 复用 [BoardNominationModal](../packages/web/src/games/werewolf/room/components/BoardNominationList.tsx) 及游戏命令。把「是否能打开」和「已经打开是否还可操作」分开，不继续用阶段条件直接卸载已打开窗口。                                                                                                                                                                                                                                                                                                                      |

房间负责捕获弹窗入口和原牌组位置。关最上层优先恢复原焦点；入口因阶段变化消失时，回落到当前可用牌组或房间信息区，不聚焦已卸载控件。旧页面保留自身路由行为，不加入房间弹窗状态机。

| 查看中出现必须确认的内容   | 房间呈现层暂缓显示；游戏层提供稳定的确认身份及当前有效性，重复快照不重复入队。关闭最后一层后用最新快照重新筛掉已失效项目，再由现有确认机制显示，不能重放捕获旧状态的提交闭包。房间或对局切换清理旧作用域待项。                                                                                                                                                                                                                                                                                                        |

### 3.4 共享手牌模型与渲染路径

实现已采用统一的 `RoomAction`、`RoomPlayerActionModel`、`RoomHostManagementModel` 和纯函数
`buildRoomHand`。玩家动作显式声明类别、观众和 `ready`／`busy`／`blocked` 状态；多行动阶段
通过 `group` 声明一个带步骤作用域 key 的子手牌。非分组阶段必须显式返回 `group: null`。

```text
房间快照 → 游戏动作／权限／角色模型
          → createRoomShellModel（检查观众、分组动作和房主任务引用）
          → RoomShell（单一导航，按当前模型构建 RoomHand）
          → RoomActionHand / RoomHandCardButton
          → 现有意图回调与确认、提交管道
```

`RoomHandDirectory` 声明稳定 key 的主手牌工具、手册入口和只读配置回调。主手牌、手册、
主持管理、玩家子手牌和舞台菜单共用同一投影；主持管理由 `task` 引用 `actions` 中的操作，
任务步骤由 `RoomHostTaskHeader` 显示。`RoomActionStatus` 与手牌分离，座位内容可在座位盘
上方显示状态，其他手牌界面则放在底部容器中。

导航只保存当前牌面和一次性焦点目标，不缓存牌面快照。进入子手牌时焦点落在返回牌，返回
后恢复到入口；选座期间暂时显示选座动作，但记忆和恢复原牌面。进入选座时焦点落在逃生牌；
退出选座后焦点回到发起入口（分组入口或主手牌上按下的牌）；入口已随阶段消失时不移动焦点，
悬空的焦点目标立即清除，不会在同 id 的牌之后出现时抢焦点。玩家选座必须声明逃生动作
（`{ kind: 'player', escapeActionKey }`），手牌缺少该牌时直接抛错。提交中的牌用
`aria-disabled` 与 `aria-busy` 保持可聚焦但不执行点击，不用原生 `disabled`，避免入口转入
提交中时丢失焦点。（2026-11-21 用户确认）舞台内容保留
`element(renderHud)`，必须显式使用 `actionSurface: 'menu'`，菜单与游戏舞台是兄弟区域。

提交状态归属在类型上显式声明（2026-11-21 用户确认）：外壳输入的 `isSubmitting` 与
`pendingActionKey` 必填，不用默认值吞掉漏传；每次 `submit` 必须给出 `actionKey`——字符串表示
由该键的手牌负责转圈，`null` 表示由弹窗或舞台自己负责（选座确认、身份弹窗等）。运行时不因
命令键找不到牌而报错：快照可能先于提交响应到达，原牌随阶段消失是正常时序，此时其余命令牌
照常锁住。

### 3.5 弹窗归属、关闭顺序与实时确认

房间槽只协调层级和时机；内容仍由游戏模块挂载，不在共享层注册九种游戏弹窗。首个纵切用下面的契约；先验证现有 Ark UI 和 `AlertHost` 的叠层关闭，再决定是否需要小范围扩展 `RoomDialog`。

```ts
interface RoomRequiredNotice<Payload> {
  // Stable within one room, viewer and round/step scope.
  readonly key: string;
  readonly order: number;
  readonly payload: Payload;
}
```

`Payload` 为游戏控制器拥有的可辨识联合，不装回调、旧快照或预构造命令。**待确认集合由当前游戏投影重新得出，不在共享层复制一个游戏事件队列。** 确认可持久化时，以快照中仍待确认的数据为准；客户端去重只用于避免重复打开同一有效项，不代替服务器确认。

| 流程                             | 接线顺序                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 玩法 → 后台到夜间 → 玩法关闭     | 普通夜间行动提示不再弹窗，在房间上方状态区显示；女巫的受袭、自救及平安夜信息只向有权限的行动玩家显示。必须确认项（如当步尚未确认的查验结果）由当前 model 投影。`RoomShell` 报告详情阻塞状态，详情退出且原焦点恢复后，游戏控制器从最新投影取首个仍有效项，接现有告警展示。已有明确用户操作触发的确认不改成后台项。 |
| 等待中同一确认重复广播／离开阶段 | 用当前作用域和 `key` 去重，同一项在当前展示期间不开第二次。条件失效则不再投影；关闭详情后不得拿旧闭包提交。点击确认再次解析当前意图，然后调用现有 `buildNightCommand` 与提交函数；网络失败沿用原重试行为。语音恢复等既有必需流程逐个核对，不全局劫持 alert 队列。                                                 |
| 本局配置 → 角色 → 关闭           | 原游戏 `onRolePress` 打开既有角色详情，父窗保持挂载；顶层关闭只回到父窗的原角色。父窗关闭才解除后台确认阻塞。                                                                                                                                                                                                     |
| 建议编辑 → 发牌／提交竞争        | 分开 `canOpen` 与 `canSubmit`。弹窗由用户打开状态决定挂载；发牌使 `canSubmit = false`，不会重新初始化草稿。提交成功走现有回执路径再关闭；若服务端先接受发牌而拒绝建议，留窗保留编辑并呈现实际理由。旧全页仍由原路由适配器处理阶段离开与返回。                                                                     |

推荐把笔记、建议表单的控制器写成**接受真实房间上下文与成功／退出意图**的内容绑定，原页面继续各自持有路由参数和返回导航；先迁共享正文及测试，再加弹窗外壳，使全页改造前后可以直接对照。建议预设选择若由 `BoardPickerScreen` 承担，弹窗复用其实际预设选择内容，在当前弹窗内部完成选择，不打开旧路由而导致房间及草稿丢失。房间关闭路径（×、受支持的键盘／返回事件）进入同一个关闭意图，脏稿先开现有确认；不要新增 history 记录来模拟页面导航。

### 3.6 夜间接线与首批可运行切片

主线 [#481](https://github.com/olveryu/WerewolfGameJudge/pull/481) 的选座状态绑定 `roomId / userId / status / stepId / effectiveSeat / roleRevealRandomNonce`。保留该边界；先沿着 `useNightInteraction` 的按钮和 `seatSelection` 输出接牌与 dock，不新建一份选座状态，也不把快照 `revision` 加入 reset 条件。对于多目标只移除变得非法的选择，未受影响目标留在原位；角色、目标类型、数量和能否跳过仍来自现有模型。音频／提交锁沿用既有 gate，不能把暂时不可操作误当成已经换步。

按以下顺序做第一条可运行纵切：

1. 在 `createRoomShellModel` 与 `RoomShell` 现有测试旁补投影及牌组测试。先让狼人杀用同一模型完整显示女巫、狼人和房主操作，验证 disabled reason、危险确认和语音锁原样保留。其他游戏在接入前仍使用原入口；同一个房间不显示两套。
2. 在狼人杀 `WerewolfRoomScreen` 把开局前使用的公开配置投影提到两处可共用的接点。开局前渲染原信息区，局中卡牌挂 `RoomDialog`；两处同时验证相同角色顺序／数量、角色弹窗与只读页脚。删掉原配置区内已迁移的建议按钮，不删除旧路由。
3. 把狼人杀玩法、笔记、建议编辑内容从路由外壳拆出；先跑现有页面测试，再补房间打开、中途发牌、关窗持久化和嵌套关窗用例。接 `BoardNominationModal` 的打开请求与可操作状态，不复制列表。
4. 接后台提示协调和 #481 选座。用多人场景让另一个座位更新时保留仍合法的目标；再让当前行动或目标实际失效，验证禁用提交或清理选择的区别。选座确定后由原命令执行，不新增 worker 或引擎分支。

## 5. 提交顺序与验收门

1. **基线与原型验收。** 先核对 Draft PR 与最新主线，安全合入包含 #481 的 `main`，不改写已推送历史或挪动用户未提交文件。原型保留在 PR 中；补上最长角色说明、完整结构的座位笔记、板型编辑和最拥挤手牌。原型确认后才进入生产 UI；房主提示样式届时收口，角色详情已明确沿用原弹窗。
2. **共享架构与狼人杀纵切。** 先保住现有动作和旧路由的测试，再接手牌、只读配置共用、弹窗协调和建议／笔记。一起迁移这条纵切的旧入口，验证选座不会被另一座位的更新打断。
3. **其他座位型游戏。** 接入阿瓦隆、秘密希特勒、谁是卧底、瞎掰王；同步更新受影响的局势、公开记录及现有 E2E；核对信息的可见范围。
4. **专属界面与结束入口。** 接入其余四款，验证进行中菜单、同步揭晓、正常结束和适用的中止。最后移除已无消费者的旧展示分支，更新 [房间外壳契约](room-shell-contract.md) 和直接受影响的架构、测试及生成器契约（仅在其确实依赖旧入口时）。
5. **交付。** 同一个 Draft PR，按可验收功能拆 commit，每个 commit 推送。不要纳入其他在改文档、工作区文件或无关原型。

验收至少覆盖：

- **模型／组件**：权限与阶段矩阵、无待办不提示、按最新快照丢弃失效确认、别的玩家更新保留合法选座、旧全页与新弹窗使用相同真实数据、发牌前后建议编辑的不同外壳行为、嵌套关闭及焦点恢复。
- **E2E**：沿用 [E2E 约定](../e2e/AGENTS.md) 和 `TESTIDS`，补改受影响的真实流程。多玩家用独立会话，按可观察阶段与动作结果同步；不通过循环打开「更多操作」来探测可选操作，不靠固定 sleep 等渲染，不弱化已有断言。用旧地址直达与返回对照验证未回归。
- **视觉／移动端**：在支持的窄屏和桌面验证最长文本、每张牌的实际可点区域、弹窗留边、独立滚动、软键盘、返回和辅助技术焦点。在真实微信 WebView 验证返回与键盘；桌面浏览器模拟不能代替真机。
- **项目检查**：受影响的 Vitest、架构契约、Web typecheck/build、lint/format、PR CI 和受影响游戏的 E2E。单 spec 按仓库 `e2e-single-spec.yml` 流程核对实际结论。所有清单行有去向及验证，安全关键的公开／私有边界验证通过，才标记迁移完成。
