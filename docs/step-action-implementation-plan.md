## 3. 怎么区分硬性决定和草稿

| 内容                                                        | 性质                 | 能否自行改动                           |
| ----------------------------------------------------------- | -------------------- | -------------------------------------- |
| 设计文档 D1–D38、接口文档 I1–I15、停点 1 标有“已确认”的条目 | 用户确认过           | 不能。要改先问用户                     |
| 接口文档“助手自定”九条、类型草图、目录和命名                | 助手的设计           | 可以，但不能因此改变上面任何一条的行为 |
| 文档里写明“助手的推论，未单独确认”的内容                    | 没有问过用户         | 实现前先问用户                         |
| 停点 1 的逐步骤大表、“措辞不变、只搬家”的清单               | 按规则认可，未逐句看 | 照做；用户在停点 3 对照快照文件再看    |

实现中遇到设计上的疑问，先问用户，不要自己定了再做。这是用户反复强调的要求。

## 4. 这次会改变的规则和玩家看得见的行为

除下面列出的以外，规则结果、播报内容、开局前流程、房主管理、警长竞选都必须和现在一样（D24）。

- 夜间操作统一成四种动作，每种一种流程（D14–D18）。吹笛者选满 2 人会自动弹确认（D16）。
- 文案按停点 1 的结论全部改写；提交后的拒绝只剩一句通用提示（D20、A17）。引导句仍是状态栏里的一段文字，不分行（D38）。
- 狼美人、恶灵骑士的座位对狼人不可选；咒狐照常可选（A19、D32）。
- 魔术师交换改为对两人的所有技能目标都互换，没有例外（D35、I5）。
- 夜报的行动句和说明句改为自动生成；被交换影响的行写“选的号码（实际为某号）”（D23、I8、I11）。
- 阿瓦隆和秘密希特勒夜间的手牌、先问弹窗、确认按钮按统一写法改（D26、停点 1 的 B11、B16）。
- 其他游戏和共享组件的确认弹窗、引导句按停点 1 的 B1–B34 改写；名单弹窗保留（D33）。
- 进行中的旧房间在上线后失效（状态结构改变，仓库既有规则允许）。

## 5. Commit 计划

共 **15 个 commit**，分三段，每段结束是一个停点。段的顺序和停点的位置是固定的；某个 commit 做大了可以拆得更细，不能把跨段的内容合并。

每个 commit 的要求：

- 所动的包类型检查通过、相关测试通过、`knip` 通过；提交信息符合仓库规则（英文、小写祈使句、标题不超过 100 字符）。
- 新代码必须在同一个 commit 里有测试引用到。旧引擎删除之前，新代码只被测试使用，`knip` 是否接受这种状态没有验证过，在第 1 个 commit 就要确认。
- 流程有意改变的 E2E 规格，跟着改变流程的那个 commit 一起改；推送后按 `e2e/AGENTS.md` 对每个改过的规格跑单规格工作流，以工作流的结论为准。
- 不改与本次无关的代码。
