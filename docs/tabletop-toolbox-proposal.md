# 聚会工具：产品与技术设计

状态：**已实现，待联机验收**。引擎、Worker、D1 与 Web 均已接入（见第 14 节）；多设备联机、容量实测与 E2E 尚未完成，本文不代表这些验收已经通过。游戏 ID 为 `toolbox`，展示名为「聚会工具」。

本文中的「已确认」来自本次讨论和[抽身份决策记录](../.grill/identity-draw.md)；「建议」是待评审的设计，不冒充用户决定；「待确认」在实施前需要决定。已有架构事实以链接的代码为准。预览中的示例和限制不是正式规则。

## 1. 产品目标与范围

聚会工具是线下朋友使用的共享工具箱，不裁判游戏、不决定胜负。房主选择工具并开始，参与者用自己的设备操作；围观者能看公开配置，但不能使用参与者的工具。

| 项目         | 首版已确认                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| 工具         | 六面骰、自定义身份牌；入口和介绍明确列出两者                                                         |
| 参与         | 房主和玩家自主入座，无座位表、不设置固定房间人数上限；至少一人入座才能开始；房主可让全部入座者站起来 |
| 观众         | 开始后新进入的人为观众，只看公开信息；锁定参与者离开、重进或断线不自动失去本轮资格                   |
| 机器人、结果 | 没有机器人、房主接管、胜负、积分、游戏奖励和游戏局数统计                                             |
| 结束         | 房主主动结束本次使用，回准备状态；重新选择工具和入座，清空本次骰子和身份结果                         |
| 身份方案     | 正式账号可保存、命名多套并跨设备复用；匿名账号不可保存。微信登录是正式账号，无须先绑定邮箱           |
| 后续         | 普通扑克牌以及其他工具不属于首版，不做提前设计出的半成品入口                                         |

「不设置固定人数上限」是产品规则，不是承诺系统支持无限请求、存储和连接。实际容量需要测量和保障，见第 12 节；不能把预览中的数字当成限制。

### 不在范围内

不实现亮骰、公开其他人的私有结果、按工具发奖励、对线下规则判胜负、为同账号多设备新增限制，也不以防作弊为由改变线下玩法。现有平台的账号、房间删除及过期行为仍然适用；具体兼容问题须在实施时验证。

## 2. 房间身份和完整流程

### 2.1 三个不同概念

1. **房间成员**：确认进入房间的账号，用于「房间总人数」；包括房主、参与者和观众。断线仍计入，主动离开后不计入。
2. **准备入座者**：准备阶段主动点击入座的账号，包括可选择入座的房主。一个账号只能入座一次；开始前可主动取消入座。参照现有游戏，主动退出房间本身不等于取消入座；再次进入时仍可通过账号找到自己的入座状态。
3. **锁定参与者**：开始时从准备入座者生成的本轮名单。连接状态和房间成员状态不改变名单；开始后进入者不在名单里，因此是观众。锁定的参与者再次进入后，按账号恢复自己的道具数据。

计数按账号而非设备或连接统计：房间总人数为已确认进入、尚未主动离开的成员数；入座人数为准备名单大小，开始后显示本轮锁定参与者数。总人数不表示在线人数，也不代表所有入座者或锁定参与者都仍在房间中。它可能小于入座或锁定参与者数；界面应分别标注，不能表达成成员数的子集。

**建议成员生命周期**：创建者确认创建成功即是成员；其他账号在成功进入并得到权威确认后加入，重复进入不重复计数。主动离开使用明确的服务端操作，提交成功后再确认退出；刷新、网络掉线、页面挂起、WebSocket 关闭都不是主动离开。网络失败时告知用户离开未确认并允许重试，不能假装计数已经改变。主动离开后的重新进入重新成为成员；若账号仍在本轮锁定名单中，恢复参与者资格。

现有 [`room_participants`](../packages/api-worker/src/platform/room/dbSchema.ts) 是历史参与数据，现有同步链路也没有在线 presence；两者都不是该成员名单。成员变更应由房间 Durable Object（DO）持久化并串行决策，和必要的房间 revision 一起提交，避免连接关闭导致人数漂移。是否将这一能力抽为平台通用机制，取决于调用路径和其他游戏语义的核实；不能擅自改变其他游戏的入房/退房行为。

**现实生命周期**：现有维护任务按房间创建时间超过 24 小时选取待删除房间，而非断线后立即清理；调度和删除 saga 的执行时间不保证恰好在 24 小时。房间被删除或过期后，成员及房间内临时结果不再承诺可恢复；账号保存的身份方案独立于房间。来源：[`maintenance.ts`](../packages/api-worker/src/platform/room/maintenance.ts)、[`roomDirectory.ts`](../packages/api-worker/src/platform/room/roomDirectory.ts)。若需更长寿命，须作为单独产品决定，不悄悄改平台全局策略。

### 2.2 状态转换

| 当前状态 | 操作                                                       | 下一状态 / 效果                                                             |
| -------- | ---------------------------------------------------------- | --------------------------------------------------------------------------- |
| 准备     | 选择工具、配置身份；玩家入座或取消；房主让全部入座者站起来 | 仍是准备；公开配置和人数更新                                                |
| 准备     | 房主开始，检查至少一位入座者及所选工具配置                 | 使用中；冻结参与者，建立所选工具的初始状态                                  |
| 使用中   | 参与者使用已选工具                                         | 仍是使用中；仅相应工具状态变化                                              |
| 使用中   | 房主提交新身份配置并重开身份                               | 仍是使用中；原身份轮次被替换，骰子不变                                      |
| 使用中   | 房主确认结束                                               | 回准备；清除工具选择、准备入座名单和本次道具结果；房间成员仍按第 2.1 节维护 |
| 任意     | 明确离开房间                                               | 移除成员；不自动取消准备入座或改变使用中的锁定参与名单                      |

不自动结束、不设回合时限或超时自动操作。房主掉线不应自动触发结束。

**房主主动退出的仓库先例**：现有游戏共用 [`useRoomEntryController`](../packages/web/src/features/room/controllers/useRoomEntryController.ts) 和 [`exitRoomFlow`](../packages/web/src/features/room/navigation/roomFlowNavigation.ts)，退出时关闭当前连接并返回首页；该路径不发送离座或解散房间命令。房主身份来自房间的 `hostUserId`，例如 [Spotmatch](../packages/web/src/games/spotmatch/room/hooks/useSpotmatchRoomState.ts) 的判断。房间删除是[单独的服务端操作](../packages/api-worker/src/platform/room/routes.ts)，不是普通退出动作。上述是代码事实，并非已完成该新游戏的端到端验证。

**建议沿用先例**：主动退出不解散房间、不交接房主，也不自动取消入座；同一账号重进时按权威房间状态恢复房主及入座身份，房间存续以现有删除和过期机制为准。取消入座是独立的主动操作。工具箱另有用户已要求的成员计数，需要在主动退出时更新成员记录，而不能误把断线判为退出。保持入座不意味着房主不能通过其他已有授权操作改变名单；具体以本工具支持的操作为准。

**全部站起来**：用户确认需要此功能。对照其他游戏的 [`canClearSeats`](../packages/web/src/features/room/model/RoomCapabilities.ts) 和 [`useRoomHostOperations`](../packages/web/src/features/room/controllers/useRoomHostOperations.ts)，在准备阶段由房主通过主持管理发起，确认后清空全部入座者，包含已入座的房主；房间成员不因此退出，房间总人数不变。没有入座者时不可操作；开始后参与名单已锁定，不提供此操作。共享确认文案当前提及机器人，工具箱不支持机器人，应复用确认和提交机制但提供符合本工具的文案，不能原样显示机器人提示。其他游戏还会通过 [`useLastActionToast`](../packages/web/src/features/room/controllers/useLastActionToast.ts) 提示受影响的玩家；本工具也应提供相应反馈，并按无座位的参与状态适配，不能伪造座位编号。

### 2.3 进入、恢复与操作顺序

建议复用现有房间定位与鉴权、HTTP 命令和 WebSocket 同步流程；在展示“已进入”及执行入座或道具动作前，完成成员登记。刷新或重连获取最新 revision 和本人投影，恢复当前阶段、入座/参与资格和自己的骰子、身份牌。`roomId` 区分重复使用的房间号；旧实例的请求不能落到新房间。

状态变化以服务端提交为准，客户端只展示可撤销的等待态，不在网络失败时自行宣布抽中或摇出结果。按钮等待中防止误点，但正确性依赖服务端原子决策和 `commandId`，不依赖按钮防重。对于结果不明的超时，使用原 `commandId` 重试或同步权威状态，不能用新 ID 盲目再抽一次。

## 3. 骰子

### 3.1 已确认体验

- 每位锁定参与者有独立骰盅，普通六面骰，数量 **1–20**，默认 **5**；固定骰子也计入总数。
- 自己摇骰、等骰盅停下后自行掀开。掀开后可固定指定骰子；下次摇骰保留固定骰子的点数，其余骰子重新摇。没有亮骰。
- 点数和固定状态由房间保存，只投影给本人；刷新、断线重连、换设备后可恢复。

### 3.2 操作设计建议

每颗骰子有稳定的本人大盅内 ID、点数及固定状态；骰盅有未摇、摇后未掀、已掀状态。摇骰在服务端产生并保存结果；动画仅呈现该次已提交结果，结束动画后可掀开。关闭页面、减少动态效果或中断动画不会再摇，也不会让掀开直接改变点数。恢复时依据已保存状态呈现，不重播导致再次决定结果。

**已确认**：修改数量在下次摇骰时生效；此前已掀开的骰子保持原样。下一次摇骰减少数量时从右往左移除未固定骰子；若目标数量小于已固定骰子的数量，提示用户先手动取消固定足够的骰子，再减少数量。不自动移除或解锁固定骰子。

**已确认**：操作会造成数量与固定状态冲突时，弹窗说明不能操作及如何修改，保持原状态，让用户自行调整。包括先减少目标数量后又尝试固定超过目标数量的骰子；不自动调高用户设置的目标数量。

**建议**沿用预览中摇动时不可调整数量的交互；未摇骰子不能固定。其余显示细节按正式组件和实际交互定稿，不因此增加额外玩法规则。

骰盅的具体构造、状态画面和动效方案见第 8.4 节。音效可独立关闭，音频不可用不影响摇骰结果；遵从系统减少动态效果设置，改用简短或无运动的状态切换。不能把 mock 的画法直接视为正式质量基准。

## 4. 身份牌

### 4.1 配置与共享牌堆

房主为每种身份填写名称、可选说明和数量，再配置每人抽牌数；首版不提供预设身份。名称、说明、各类型初始数量和每人抽牌数是公开配置；可在准备时查看。至少一位参与者入座，且 `身份牌总数 >= 锁定参与人数 × 每人抽牌数` 才能开始；多余牌留在共享牌堆。身份名称不能为空，身份数量及每人抽牌数必须是正整数且计算不能溢出；名称、说明与数量的具体输入容量上线前按第 12 节确定，不沿用 mock 上限。

**已确认**：同一套配置中的身份名称不能重复；相同身份用数量表示，不能用两条同名身份分别配置说明。判断重名与方案名一致，忽略首尾空格、区分英文大小写。名称重复时在对应字段提示修改；载入、保存、开始和重开也须在服务端验证。

每位参与者从**同一个**牌堆逐张随机抽取，抽走不放回，直至自己的配额满。客户端只发送“我要抽一张”，不能提交目标身份或指定自己拿到哪张。抽牌提交时同时减少牌堆、增加本人手牌并推进版本；并发请求由同一房间权威状态串行决定，同一命令重试不重复抽。保留剩余牌，不要求参与者一次抽完，也不设身份查看门槛。

展示自己的已抽牌和说明；关闭后可再次查看。牌背、翻牌及手牌管理参考本项目共享组件，不因动画失败而影响已提交结果。房主作为参与者只能查看自己的牌；作为房主也不能直接查看其他人的抽牌结果。观众不能抽牌，也不能获取别人的结果。

建议仅公开总剩余张数，而不公开**按身份分类的实时剩余数量**、未抽顺序或随机种子：分类剩余可能直接揭示被抽走的身份。即使如此，公开的初始配置和现场信息仍可能使玩家推断他人身份，产品不承诺防止推断。

### 4.2 身份重开

房主在使用中可修改身份配置并重开身份轮次；提交前原轮次仍正常，成功后一次性替换配置、牌堆和所有人的身份牌。本操作不改变锁定参与者、骰子或其他工具。新配置按本轮锁定人数检查牌数，不能按当前在线数或当前成员数计算。

沿用其他游戏对清空本局数据的确认方式，重开前说明：“重开后，本轮已抽身份将清空，骰子不受影响。”取消则原轮次不变；若编辑期间房间已结束或身份轮次已被另一操作替换，拒绝旧提交并提示刷新。确认交互复用现有 [`confirmAction`](../packages/web/src/features/room/confirm.ts)，不是新增弹窗体系。身份轮次有独立 ID，抽牌请求带预期轮次 ID：晚到的旧请求不能抽到新一轮。身份重开不意味着重新选择全局工具，也不新增游戏局数。

## 5. 已保存身份方案

### 5.1 用户流程

房主可以查看自己的方案列表、载入、另存新方案、明确更新已有方案、重命名和删除。方案包括名称、身份定义和每人抽牌数，**不包括工具选择、玩家、已抽结果或牌堆**。载入到房间时复制内容，之后编辑只影响当前房间；除非用户明确选择「更新原方案」，否则不改账号保存的版本。匿名用户可以在房间中配置，但保存、列表及修改操作提示登录，不要求正式微信账号绑定邮箱。

**已确认**：同一账号不能保存同名方案；新建或重命名遇到同名时提示用户修改名称。方案仍通过稳定 ID 而非名称识别。

删除和覆盖前沿用现有确认交互；关闭有未保存修改的编辑界面时，沿用[房间设置的放弃修改确认](../packages/web/src/features/room/config/createGameConfigScreen.tsx)。保存失败保留本地编辑并展示可恢复操作。若多人或多设备同时编辑一个保存方案，服务端使用版本条件更新；冲突时显示「方案已更新，请重新载入后再保存」，不静默覆盖。

### 5.2 数据与账号

建议在 D1 建立游戏自有方案记录：稳定 ID、所属用户 ID、方案名、受严格 schema 校验的配置、版本号、创建和更新时间；按所属用户索引。列表、读取、创建、修改和删除均从认证上下文取 owner，绝不信任请求中的 owner；每个操作校验正式账号及资源归属。复用 [`requireNonAnonymous`](../packages/api-worker/src/features/auth/tokenAuth.ts) 的语义，而不是以“有邮箱”为条件。输入用现有严格解析及参数化数据库访问；用户文字作为文本渲染，不当作 HTML。

账号合并必须保留方案：现有[微信绑定/合并流程](../packages/api-worker/src/features/auth/routes.ts)会删除来源账号，不能只加一个 `ON DELETE CASCADE` 外键然后丢弃其方案。**已确认**：两账号存在同名方案时两套都保留，将微信账号的方案自动改名，例如「狼人杀（微信）」；若改名后仍冲突，加数字区分。建议迁移来源方案到目标用户并保留方案 ID 和内容；把归属迁移、相关校验和来源账号删除纳入实际支持的同一 D1 原子批次，并检查并发写入及失败回滚；若合并流程无法满足这一原子性，应先设计一致的合并流程，不能先删账号再异步补救。现有账号合并中其他数据的语义不因本功能改变。

列表示例、编辑和合并需要验证 schema、外键、索引、读写成本及迁移；账号删除应遵循现有账号删除和数据保留政策，不为本工具暗中保留孤儿记录。方案容量、文本长度和总数据量上限需要基于部署与实际体验设计，并在 UI 和服务端使用同一规则；数值不是本轮已确认决定。

## 6. 权威状态、权限与命令

以下字段和命令名为**建议的领域模型**，不是已存在的接口；具体命名以实现时项目协议为准。

### 6.1 权威状态和不变量

DO 内房间权威状态包含房间身份、阶段和成员；准备阶段包含已选工具、公开配置与入座账号集合；使用阶段包含本轮标识、锁定账号集合、每个启用工具的状态。身份工具包含轮次 ID、配置、各类型剩余数量、每人抽牌配额和本人已抽牌；骰子工具包含每位参与者各自的骰盅。

- 集合以账号标识去重；锁定参与者从开始瞬间的入座集合产生，不由连接数或成员总数推导。
- 所有身份类型的 `剩余数量 + 本轮已抽数量 = 配置数量`；每人的已抽数不超过配额；所有数量非负整数。
- 当前骰子数量和下次摇骰的目标数量分别记录，均在 1–20；未摇时没有当前结果。已固定的骰子有合法点数；动画状态与权威结果不混淆。
- 未启用的工具没有可操作的状态；全局结束后旧轮次不可操作。身份重开只替换身份子状态。
- 严格解析当前持久状态：字段缺失、数量矛盾、阶段与工具不一致等是破损状态，记录安全的错误上下文并 fail fast；不凭空填默认值或继续广播损坏的数据。正常用户输入不合法则给出可读拒绝，不作为内部异常。

按身份剩余数量加权逐张抽取是一种可选实现：每次在当前总剩余范围抽索引，按类型累计区间选中后减一，不需要向客户端发送牌堆顺序，也无需先物化每张牌。该实现需覆盖数量边界、随机源范围和整数安全；若容量测量显示不合适，应选可验证的等价实现，不自行变更玩法。

### 6.3 并发、回执和随机

沿用现有 [`CommandPipeline`](../packages/api-worker/src/platform/commands/CommandPipeline.ts)：命令以 `commandId`、主体及请求内容查回执，决策及状态、回执和 outbox 在 DO 事务内提交；相同 ID 不同请求应冲突。现有回执在有引用中的 outbox 时不会提前清除，通常保留七天，见 [`CommandReceipts.ts`](../packages/api-worker/src/platform/commands/CommandReceipts.ts)。这里的幂等承诺以回执实际保留期及房间存续为边界，不宣称永久 exactly-once。

命令的版本/轮次检查防止迟到的操作作用于新的骰盅或身份轮次；不同参与者同时抽牌均从提交时的同一个剩余牌堆决策。回执保存快照，可能包含旧轮次私密数据：输出必须按请求者授权投影，客户端不得让旧 revision 覆盖较新的房间状态。重置后界面不显示旧结果；如果将来要求物理即时擦除，必须另行设计回执清理与重试保证，不能声称现有回执已擦除。

当前命令管线生成随机种子，引擎通过 [`random.ts`](../packages/game-engine/src/platform/random/random.ts) 的 seeded RNG 保持纯决策；其种子被归约到 32 位，现有整数映射也不是严格无偏的密码学抽样。建议首版沿用确定性决策和原子回执的架构，明确这不是密码学防作弊承诺；实现时按骰面与加权牌堆范围评估分布与取值范围，不能把有限随机空间误称无限或绝对公平。若引入更强随机算法，必须保持可重试、纯引擎和原子提交，不擅自替换其他游戏随机行为；算法和范围由实现评审及测试证据决定。种子、内部牌堆和私有结果不传给未授权客户端，也不写日志。

## 7. 隐私、投影和可恢复性

| 数据                                            | 房主           | 本人参与者 | 其他参与者 / 观众 |
| ----------------------------------------------- | -------------- | ---------- | ----------------- |
| 已选工具、公开身份配置、成员及入座计数          | 可见           | 可见       | 可见              |
| 自己的骰盅及固定状态                            | 自己入座时可见 | 可见       | 不可见            |
| 自己抽到的身份及说明                            | 自己入座时可见 | 可见       | 不可见            |
| 他人骰盅、身份、牌堆内部剩余类别/顺序、随机种子 | 不可见         | 不可见     | 不可见            |

无座位界面不需要广播每个人的私有状态或完整参与名单；客户端拿到公开摘要及自己的参与状态即可。公开配置本来包含身份名称和说明，它们不应被误当作秘密，但抽牌结果仍是私有的。

现有 DO 已提供按用户投影机制；必须核查并覆盖**全部**对外读取，包括首次同步、`SYNC_RESULT`、`STATE_UPDATE`、HTTP 命令结果、重复命令回执、错误、可用的其他读路径以及重连。不能通过完整权威快照再靠组件隐藏。对身份与骰子的本人状态，严格区分“未产生”和“已裁剪”，避免解析器把缺失当正常默认。权威持久状态的校验必须比客户端投影严格；若现有同一 state 类型/codec 无法表达两者，扩展类型与 parser 契约并更新调用及测试，不用类型断言或宽松解析掩盖问题。可参考 [`spotmatch` 房间测试](../packages/api-worker/src/games/spotmatch/__tests__/room.test.ts)，但不预设它直接覆盖本工具。

回执由相同主体绑定，且可能是旧快照；重放时仍必须检查正确用户投影及 revision。浏览器内按当前账号/房间隔离缓存，退出、账号切换和房间实例切换时移除旧视图；服务端鉴权始终是边界。不得把私有结果、牌堆或随机种子放入日志、错误上下文、埋点或 Sentry 附件；审查所有异常及请求日志，而不仅是业务 logger。

## 8. 页面与交互

### 8.1 创建和准备

1. 游戏入口以「聚会工具」和简短介绍展示骰子、身份牌。创建时默认选中骰子，至少选择一个工具；全部取消时提示先选择工具。房主也可以只选身份牌或同时选择两者。
2. 准备页使用真实房间外壳、邀请、玩法、主持管理和公开配置卡，显眼显示已选工具；房主可以从主持管理的「房间设置」修改工具。开始后设置入口锁定并说明原因。
3. 页面中央用真实账号头像和已有装饰呈现自己的状态：未入座时「请入座」，已入座时「已入座，等待房主开始」。状态文字大而清楚，配合颜色、图形而非仅靠颜色区分；手牌提供「入座 / 取消入座」，主持管理提供「全部站起来」。点击自己的形象可打开真实个人资料。
4. 清晰显示「已入座 N 人」「房间共 M 人」，不绘制座位表；分享、返回、资料和房主操作与共享房间语义一致。其他玩家的形象是否需要列表不因复用组件而强加给产品。
5. 启用身份时，身份选择采用可辨认的按钮/选择态；编辑采用分区或 tab，避免所有项目堆成长页；每人抽牌数和总牌数固定在编辑区域底部，并显示当前需要的牌数。固定区要避开安全区、键盘和内容，不能遮住表单或操作按钮。

### 8.2 使用中

工具箱清楚展示已启用的工具；参与者可切换骰子和身份牌，各自保留状态。骰盅突出摇、停、掀、固定和数量；身份工具突出「抽一张」、已抽数/配额、自己手牌、剩余总数和公开配置。身份牌关闭后仍有明显入口再次查看。观众看到公开配置与观看状态，不展示可误点的私人操作。房主有「重开身份」和「结束本次使用」；确认说明清楚哪些数据会被清空。

加载、无工具、还未摇骰、未抽牌、抽满、观众、断线重连、保存失败和配置冲突都有明确文案与后续操作。对于未知失败，走统一错误管线，不显示成功态；服务端拒绝与客户端禁用原因应一致。

**身份配置工作区**：

- 顶部使用单行标签「身份」「已保存方案」；选中状态包含文字和标记，标签过多可横向滚动。匿名用户可配置身份；方案标签说明「登录后可保存和使用方案」，不阻碍房间内配置。
- 「身份」区顶部是「添加身份」按钮；每种身份是可操作卡片，显示名称、数量及说明摘要，并提供清晰的编辑和删除入口。空状态写「还没有身份，添加身份后才能开始」。新增/编辑使用带明确标签的表单：身份名称、可选说明、数量；表单错误标在对应字段旁。删除针对当前房间草稿，保存方案不会被隐式删除。
- 编辑区底部固定摘要和主要操作：显示「每人抽 N 张」「共 M 张」「需要 K 张」。身份数量不足时同时显示缺口及「请增加身份牌数量」；`K` 以当前准备入座数或使用中锁定人数计算，依据所处阶段明确标识。底栏位于可滚动内容之外，预留等高空间，避开设备安全区；软键盘出现时保证输入和提交可见，不盖住末项。
- 「已保存方案」列出本人方案名称、身份数量和每人抽牌数；每项有「载入」与明确的更多操作。保存新方案要求名称；对已有方案的更新、重命名和删除分别执行，覆盖和删除需确认。载入仅替换当前编辑草稿；草稿未保存时先确认，账号方案本身不变。
- 准备阶段提交配置更新房间；使用中编辑身份重开时保留原轮次，提交前显示清空身份、不影响骰子的确认。失败后保留编辑内容，允许重试或按冲突提示重新载入。返回或关闭含未保存修改的界面走现有放弃确认。

**身份使用工作区**：

- 一张可识别的牌背为主要「抽一张」操作，旁边显示「已抽 N / 每人 M 张」和「牌堆剩余 K 张」。点击后显示提交中；只有服务端确认后才呈现翻牌结果，失败保留原进度并给出重试。
- 新牌展示名称与可选说明，并可关闭；「我的身份牌」始终可重新打开，按本人抽取顺序展示。抽满后改为「已抽满」并保留查看入口；无需等待其他人。未抽牌时给出「还没有抽到身份」。
- 房主和其他人看到的配置及总余量与本人手牌分开；不向观众显示空的“我的牌”占位以免误导。公开的配置可导致现场推断，不承诺匿名或防推理。

**连接与异常**：初次进入显示「正在进入房间」；断线显示现有连接状态，保留上次快照但禁止提交需在线确认的操作；重连后按最新 revision 更新。提交超时显示「结果确认中」，用同一命令 ID 重试或同步；不能自动使用新 ID 再抽。房间不存在、认证失效、配置冲突和服务失败使用现有错误管线与可执行的返回、登录、重新载入或重试动作，不把断线显示成主动离开。

### 8.4 骰盅视觉与动效提案

**画面构造**：用桌面上一只可辨认的倒扣骰盅作为主视觉，而不是抽象圆球或简单图标。盅体采用上窄下宽的圆角截锥、椭圆口沿和底部接触阴影；深色织物/皮革感以克制的明暗与细纹表现，边缘有轻微高光，不使用脏旧贴图或金属粗边。掀开时盅体与桌面分离，露出立体浅色骰子；骰面点数、边缘和阴影要清楚。盅体、骰子、文字和按钮均需与背景保持辨识度。

| 状态        | 主视觉及说明                                                                                                      | 唯一主要动作                           |
| ----------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 未摇        | 盅体静止，旁边写「准备好了吗」；数量选择显示下次骰数，默认 5                                                      | 「摇骰」                               |
| 提交中/摇动 | 盅体封住点数，摇动有方向变化、碰撞节奏与逐渐停稳的缓动，不透出骰面；服务端尚未确认则提示「正在摇骰」              | 不接受重复摇骰或修改骰数               |
| 已停、未掀  | 静止盅体及「摇好了，自己掀开看看」                                                                                | 「掀开骰盅」                           |
| 已掀        | 骰子稳定排列，点数清晰；每颗可按压切换固定，固定项有图标和文字状态，不只靠颜色；同时展示「已固定 N 颗」和下次骰数 | 「再摇一次」；可单独设置数量及切换固定 |
| 数量冲突    | 保留当前骰子和目标数量，弹窗解释固定数量与目标不兼容                                                              | 「知道了」，用户自行取消固定或调整数量 |

**运动节奏建议**：收到权威结果后，本地呈现约 1.2 秒的摇盅：短促起动、数次逐渐减幅的左右/轻微旋转、最后回到桌面并静止。该时长是视觉评审的初始参数，不是服务端计时或已实测结果；掀盅由玩家主动触发，盅体向上偏移并稍旋转，骰子保持最终点数，约 0.3 秒内完成。不能把自动掀盅、骰子在桌面直接滚动或公开点数引入玩法。

结果先由服务端提交，客户端的动画不决定点数；动画执行、取消、页面切换、音频失败或浏览器不触发结束事件都不能阻塞状态进入可掀开阶段。刷新时直接按权威状态显示静止画面；重复回执或旧 revision 不得重播成新结果。系统启用减少动态效果时用近乎即时的静态状态切换，仍保留「摇好了」和手动掀盅。音效建议采用短促的盅内碰撞、停稳和掀盅声，遵循现有声音设置，另给道具音效开关；浏览器未授权播放时静默不阻碍操作。美术实现先比较 CSS/图形资源与实际设备的效果和性能，不为“物理模拟”强加 3D 引擎或新依赖。

数量控件使用带标签的减号、当前目标数和加号；数量为 1–20，不能只依赖滑动操作。展示「下次摇 N 颗」，已掀开的旧结果不随调整立即增减。骰子按稳定顺序显示；固定态使用可访问的切换按钮语义和如「第 2 颗，点数 4，已固定」的名称，右向左移除未固定骰子的规则按第 3 节执行。小屏换行时逻辑顺序不随视觉折行改变。参考 [Saikoru](https://shin-yu.net/nyups/saikoru/zh/) 的立体感和停靠节奏，不复制其代码、宣称其算法或改变已确认的骰盅流程。

### 8.5 复用与无障碍

优先复用现有房间外壳、[`RoomGameSummary`](../packages/web/src/features/room/components/RoomGameSummary.tsx)、主持管理、弹窗/手牌、头像、装饰、资料、主题 token 和错误反馈。预览仅提供视觉探索；只有拆分后满足生产状态、权限、可访问性和测试的组件才能复用，不把预览服务或虚构数据接入生产。

共享 [`RoomViewer`](../packages/web/src/features/room/model/RoomViewer.ts) 已可明确表达无编号座位的参与者；[`RoomCapabilities`](../packages/web/src/features/room/model/RoomCapabilities.ts) 的资料 target 和 [`useRoomProfileController`](../packages/web/src/features/room/controllers/useRoomProfileController.ts) 也可定位无座位的人类账号，编号座位的踢人和离座操作仍受限于真实座位。这些仅是共享接缝，工具箱尚未接入；仍需核查房间 shell、能力派生、动作处理和其他游戏的行为。头像资源与装饰加载使用已有真实账号链路；失败交由现有图片/错误策略处理。

目标是满足适用的 WCAG 2.2：语义化按钮/表单、明确标签和选中状态、可见键盘焦点、操作与对话框焦点管理、颜色以外的状态信息、足够对比度、适当触控目标，以及向辅助技术通告重要状态变化。减少动态效果不改变游戏结果；按实际浏览器和微信 WebView 验证。不能用“2026 风格”代替可用性和项目设计语言。

## 8A. 数据边界与关键实现设计

本节是可评审的实现方案，不表示接口或迁移已存在。新游戏使用同一 DO 串行决定状态变化；引擎不访问网络或数据库。命令携带的用户身份只能由认证上下文建立，客户端不得提交替他人操作的用户 ID。

### 8A.1 房间状态与视图

权威状态按领域划分：共同部分是房间身份、成员账号集合和阶段；准备部分是选用工具、身份配置草稿和准备入座账号集合；使用部分是本次使用 ID、冻结参与账号集合，以及各已选工具的数据。骰子按用户保存目标数量、当前骰子、固定标记、盅体阶段和版本；身份按独立轮次保存公开配置、各类型剩余数量和按用户保存的已抽牌。成员集合与准备/冻结集合独立，成员主动退出不隐式修改后两者。

网络视图只包含公开房间信息、两个计数、当前用户的成员/入座/参与状态，以及该用户获准访问的骰盅和身份牌；它不包含全体用户的私人 map、按身份分类的剩余数或随机种子。**本人状态缺席**与“尚未摇/尚未抽”分别表示，观众不获得可伪造成他人结果的空私人结构。持久化 codec 严格验证全量权威状态及数量守恒；网络 codec 严格验证公开视图和本人私有视图。两者各有明确类型和 parser，不把已裁剪状态交给必须解析权威状态的代码。

[`workerModule.ts`](../packages/api-worker/src/platform/gameModules/workerModule.ts) 已开始扩展该接缝：权威状态 codec 继续用于决策、持久化和回执；游戏可另行提供视图 codec，对每个投影结果校验结构和房间身份。未提供视图 codec 的既有游戏继续使用原状态 codec。现有 Spotmatch 把不属于本人的字段设为 `null`，不改变其网络形状。本工具仍需实际实现独立视图与客户端 codec，并验证同步、广播、HTTP 和回执重放；扩展接缝本身不是隐私验收。

回执在事务内保存原始决策结果以满足现有重试语义；在每次对外输出时按已验证的回执主体投影，包括首次 HTTP 返回与重放。旧回执只能返回给原主体，旧 revision 不能覆盖新状态；不向客户端暴露权威快照。隐私验收检查原始 HTTP 和 WebSocket 帧，不只检查页面。日志、异常和开发工具也不输出原始快照。

### 8A.2 成员与房间外壳

成员登记和主动离开建议作为工具箱专用权威命令，复用平台认证和命令幂等，而不是依赖 WebSocket 连接数。创建者初始化即登记；进入时先确认房间实例与认证，再登记并同步；主动退出必须等待服务端确认，超时保留原 ID 重试。一个账号多设备登记只算一个成员；一个设备断线不移除。对另一个设备主动离开后仍可能发出的命令，重新进入前应按成员权限拒绝；锁定资格保留，再进入后恢复。成员操作与开始、重开、结束都经过同一 DO 顺序，不从 D1 历史表推断即时成员。

扩展共享 shell 的 viewer/动作受众：区分「有真实座位的参与者」「按账号入座的参与者」「观众」，资料 target 可直接按账号定位；踢人/座位操作仍只能使用真实座位。房主身份与参与身份继续正交。无座位布局不创建假座位或隐藏座位网格，房间头像、装饰、资料、邀请、主持管理和状态反馈复用现有生产链路。平台能力、组件及其他游戏契约测试随此更改，避免改变其 bot 接管或座位权限。

### 8A.3 方案记录与账号合并

建议 D1 独立表以方案 ID 为主键，列包含 owner、名称、严格校验后的身份配置、版本及时间；对 `(owner, name)` 建唯一约束并索引 owner。**已确认**：名称比较区分英文大小写，并忽略首尾空格。技术上建议写入前按 NFC 规范化，显示和冲突判断使用同一规范化值。更新、重命名、删除以 owner 和版本作条件；资源不存在、无权与版本冲突按既有 API 风格返回，不能跨账号枚举内容。

账号合并时，在可回滚的一致性单元内迁移来源方案并保留 ID、配置和版本，保留目标同名方案。来源同名时依次尝试「原名（微信）」「原名（微信）2」「原名（微信）3」；**与目标已有名称及本次已分配名称都比较**，使用同一规范化规则。必须避免先在事务外读完名称、再无条件覆盖：可在 D1 原子批次中以唯一约束保护迁移，检测并发冲突后回滚、重新读取并重算，仍无法完成则明确失败且来源账号未删除。来源迁移及删除必须在同一个成功批次中；还需验证账号合并前已发出的并发方案写入不能在来源被删除后产生孤儿或静默丢失。若现有合并流程不能提供上述保证，先调整合并流程再上线，不能通过异步补偿宣称原子。

### 8A.4 平台生命周期与随机数

工具箱没有玩家游戏局数和奖励，但现有 [`platformEffects.ts`](../packages/api-worker/src/platform/room/platformEffects.ts) 对所有从非 ongoing 进入 ongoing 的房间生成 `platform.room.gameStarted`，并更新管理后台 `rooms.games_started`。这是**房间运维元数据**，不是账号完成局数；不应误称当前平台完全不会记录开始事件。建议继续保留房间开始元数据，禁用工具箱的玩家完成事件、玩家局数和奖励；若产品也要求后台不记录开始，需另行确认并修改通用生命周期契约。

现有 32 位 seeded RNG 只能提供有限随机状态；确定性重试不是密码学公平证明。首版按第 6.3 节使用现有决策注入方式并验证范围、数量守恒和确定性，不以少量样本测试证明无偏；若实测配置范围超出可接受的随机模型，先评审替代算法和迁移影响，而不是截断数量或悄悄修改其他游戏。

## 9. 平台接入与合理抽象

### 9.1 特征与生成器

建议首版声明意图：`identity=none`、`night=none`、`guidedNarration=none`、`stageDeadline=none`、`wordSupply=none`；其中 `identity=none` **只表示不启用现有统一发身份/查看门槛功能，不表示没有私密牌数据**。本工具的逐张抽牌需要独立的权威规则和隐私投影。`identity=private` 会带入座位、统一查看及机器人语义，不满足本设计，不能为了省事选它。

当前生成器强制 `botsAndTakeover`、`hostConfig`，强制业务统计并生成默认奖励；[能力生成](../scripts/lib/new-game/features.mjs)、[生成过程](../scripts/lib/new-game/generate.mjs)和[游戏注册](../packages/game-engine/src/games/registry.ts)均可见这些约束。

**实现决定（已落地）：** 聚会工具是唯一的工具型游戏，没有第二个使用方，因此没有为它改造生成器，而是按生成器的登记点逐项手工接入，并用显式声明代替伪造数据：

- 引擎注册 `rewards: { policy: 'none' }`：不发完成事件、奖励或局数统计；账号统计面板按该声明跳过（`GameStatsPanels` 测试以注册表为准）。
- 无编号座位、无机器人：座位点击组合、接管横幅和复盘三个跨游戏契约为 `toolbox` 显式登记豁免并说明原因，同时断言它不走共享座位处理器、复盘永远为 `notEnded`。
- 生成器的复盘契约锚点随之更新，生成器测试在 `toolbox` 存在时仍全部通过。

若将来出现第二个工具型游戏，再把这些声明提升为生成器特征，而不是现在预先抽象。

保留 `hostConfig` 意图，同时支持准备阶段启用工具及使用中仅重开身份的不同权限；不能将后者误当作全局房间设置未锁定。扩展能力时优先复用现有能力来源，不建立互相矛盾的第二套声明；对旧游戏保留原机器人、奖励、统计和身份行为，覆盖回归。

### 9.2 注册与产品能力

获得设计批准后，调整生成器和相应契约，再按新游戏流程生成并登记引擎、Worker、Web 目录、静态工厂、公共入口及需要的 D1 游戏注册迁移；保留并逐项处理生成报告。新账号身份方案 API 是游戏自有 HTTP 路由，登记到已有路由组合及 registry；其表与索引由迁移明确创建。不开启词库、语音引导、夜晚、自动计时、战绩回放或胜负结算；仅在现有代码证实需要的接缝增加类型，不预先新建抽象。

上线前验证首页/创建入口、worker 路由和生产可见性，不把“已注册但隐藏”当成产品上线。没有完成局数意味着账号页不展示该游戏的局数统计，既不创建业务统计表，也不向通用完成事件、奖励或结算 outbox 发事实。运维层的请求数、错误和延迟不是玩家游戏局数。

## 10. 错误、日志与安全

引擎只返回可分类的规则拒绝或抛出不变量错误，不依赖网络或日志。Worker 使用项目 [`createLogger`](../packages/api-worker/src/platform/observability/logger.ts)，Web 使用现有 logger 和 [`errorPipeline`](../packages/web/src/utils/errorPipeline.ts)：预期业务拒绝提供用户可理解的反馈，异常通过现有 Sentry 通道上报。记录可检索的事件名、模块、房间实例标识、`commandId`、阶段、操作类型、结果类别/原因码、耗时、revision；按需用内部匿名化/最小化的主体标识关联，遵循现有数据保护政策。

不记录 token、邮箱、完整请求体、用户自定义文字、骰点、身份结果、剩余分类、牌堆、种子或保存方案内容。错误消息和 Sentry 自动捕获同样需要检查和脱敏，不能把原始 schema 错误或异常对象原封不动地携带私密输入。预期校验失败不刷错误告警；破损状态、提交失败和无法恢复的内部错误记录可定位原因，向用户显示可行动的通用信息，不吞错或返回假成功。

账号和资源权限在服务端每次检查；请求必须限定当前房间实例与当前用户。对认证、限流、非法输入、并发冲突、存储不可用分别返回清晰结果，复用现有平台协议与速率限制。日志指标建议观察进入、开始、抽牌、摇骰、重开、结束、方案保存的成功/拒绝/失败率和耗时，以及投影/存储错误；不采集玩家结果来做统计。

## 11. 部署、恢复与数据生命周期

- **房间数据**：DO SQLite 保存权威状态和命令回执；房间结束仅清空本次工具状态，房间删除/过期通过既有 saga 清理。刷新、断线及部署导致连接中断后通过重新同步恢复；恢复的前提是房间和认证账号仍然有效。
- **账号数据**：D1 方案跨房间、跨设备持久化，走正式账号权限、迁移和账号合并流程；房间结束不删除方案。没有对旧版持久状态做兼容迁移的承诺，遵循项目当前 state codec 规则。
- **跨存储边界**：保存账号方案和修改房间配置是独立操作，不假设 D1 与 DO 跨库事务；载入时复制已成功读取的方案，再通过房间命令独立提交，失败时显示哪一步失败。账号合并涉及的 D1 变更必须作为一个明确的一致性单元。
- **发布**：先评审并部署数据库迁移和向后兼容的共享平台变更，再发布引擎、Worker 和客户端的配套版本；新游戏在完整接线和验收前不对用户可见。验证迁移重复执行/部署顺序按项目实际迁移系统执行，不假设任意迁移可重复运行。回滚应保留账号方案数据，并核实运行中房间的兼容及删除风险。

## 12. 容量与性能

不加未经批准的固定房间人数上限，也不声称无限容量。DO 的连接、消息、CPU 和存储存在平台限制，参见 [Cloudflare Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/)。[D1 limits](https://developers.cloudflare.com/d1/platform/limits/) 当前列出的单个字符串、BLOB 或表行上限为 2,000,000 字节，表行还包含其他列；[Workers limits](https://developers.cloudflare.com/workers/platform/limits/) 的请求体上限取决于域名套餐。这些是提供方边界，不是可用配额或建议的产品上限；上线前应复核当前套餐、运行时、消息和存储限制。

### 12.1 规模和成本模型

令 `P` 为锁定参与者数、`M` 为当前成员数、`C` 为同房间连接数、`R` 为身份种类数、`D` 为每人骰子数、`Q` 为每人抽牌数。准备阶段牌数条件为 `总牌数 >= P × Q`；检查正整数和安全整数后，可用 `P <= floor(总牌数 / Q)` 避免乘法溢出。方案配置、房间状态、投影、回执和消息都以 **UTF-8 序列化字节数**测量，不能用字符数代替，行大小还需计入其他列和格式开销。

- 权威状态大致随成员、参与者、骰子、身份类型与已抽牌增长：`O(M + P + P×D + R + 已抽牌数)`；按类型计数的牌堆不需要物化全部未抽牌。
- 每次提交目前会保存状态和回执，回执包含结果快照并通常保留七天；粗略存储增长为 `提交次数 × 平均回执字节数`，加当前状态、索引、outbox 等。例如平均回执 100 KB、3,600 次提交约 360 MB，**只是计算示例而非测量值**。必须测量回执累积、清理和峰值，不能只测单个快照；如超出可接受成本，评审压缩/回执形状等平台级改变及幂等影响，不能缩短保证而不说明。
- 每次状态广播的总流量约等于各连接对应投影字节数之和；`C` 个连接不等于 `M` 个成员，同账号多设备各需要同步。投影不包含他人手牌和骰盅，避免随着所有人的私人结果增长而放大每个连接的消息。
- 姓名、说明、种类数、数量及保存方案数的输入大小既影响 UI 也影响数据库、单条回执和广播。客户端即时显示错误，服务端独立校验相同规则，D1 和 DO 均不能只依赖浏览器限制。非法输入返回可理解的字段错误；存储/资源失败不提交部分状态、不返回成功，记录不含用户文本或私人结果的错误原因并提供重试或调整入口。

### 12.2 实测与发布门槛

以下是**待评审的测试方案和目标，不是已完成的测量，也不是人数限制**：

1. 在隔离的、配置与生产一致的测试环境，使用合成账号和配置，以 1、10、30、100 个参与者/连接分别执行进入、同步、并发抽牌、连续摇骰、身份重开和断线恢复；再覆盖同账号多设备、观众、成员数与锁定数不同、最大经过批准的配置，以及 100 人以上的探索性测试。记录负载、客户端数、网络条件、样本量和部署套餐；不要向第三方发送真实用户数据。
2. 每个规模至少收集 200 次相关操作，并报告成功数、拒绝数、异常数、p50/p95/p99 的提交和可见同步耗时、快照/回执字节、累计存储及广播总字节。单客户端端到端耗时从点击发送至该设备收到不早于提交 revision 的投影；服务端延迟另计。比较基线其他游戏和环境，区分网络、DO 和客户端渲染。
3. 建议在规定的测试网络与设备下，正常容量场景中成功操作的端到端 p95 不超过 2 秒，抽牌/摇骰的丢失、重复提交和跨用户泄漏均为 0；非故意错误的服务端 5xx 为 0。该目标及哪些实测规模构成发布容量须结合真实设备、套餐和成本评审，未通过就优化或重新讨论，不将目标数字当作已验证承诺。
4. 方案文本、种类数与数量分别做边界、中文及 emoji UTF-8 字节、组合规模和 D1/DO 实际写入测试；覆盖安全整数与乘法溢出、存储接近服务商限制、回执累积和删除清理。根据结果提出可解释的字段与整体容量预算及用户文案，涉及产品限制先获得确认；不要沿用 mock 的 40 字、300 字或 200 张。
5. 确定告警和运维阈值时，以已测量的正常峰值与所用套餐上限留余量，观察拒绝率、延迟、状态/回执字节和存储错误。若需要保护单行存储，应在事务前对**实际完整序列化结果**进行预算判断并拒绝整个变更；预算需考虑未来动作、回执和数据库行开销，不能以“当前状态刚好能写入”冒充可继续使用的保证。容量策略、限额数值及其 UI 尚未获批准，是上线门槛。

## 13. 验收与实施顺序

实施顺序：① 平台工具型契约及生成器；② 生成、注册和无座位房间成员/资料；③ 引擎的阶段、骰子和身份领域逻辑及按用户投影；④ D1 方案与账号合并；⑤ 真实客户端；⑥ 端到端验收与发布接入。隐私投影接缝可作为并行前置工作。每阶段保持其他游戏行为；生成报告逐项记录完成证据或经批准的不适用原因，不因代码生成成功就标完成。

**针对性测试：**

- 引擎：入座/取消、房主让全部入座者站起来的权限及阶段、开始前置与锁定；各工具互不影响；骰子边界、固定/数量调整及重试；身份名称重复拒绝、数量守恒、多用户并发、每人配额、牌不足、身份重开和过期轮次命令；结束返回准备、不生成奖励或局数事实。
- Worker / DO：成员入房、主动离开、重复提交、断线不减人数、重进恢复、房间实例隔离；事务中断、同 ID 相同/不同请求、旧回执及 revision；逐用户核验每条同步、广播、命令回执及重试路径，包含房主和观众；日志及异常不暴露秘密。
- D1 / API：匿名、正式微信及邮箱账号权限；方案 CRUD、归属隔离、重复身份拒绝、复制后编辑、明确更新、版本冲突；来源/目标账号同名方案合并、失败回滚、删除账号及迁移；并发写入和预期限额。
- Web：真实共享房间入口、主持管理的房间设置、头像装饰及 profile、无座位观众/参与者、身份 tab 与固定统计栏、骰盅、加载/失败/重连、键盘/辅助技术和减少动态效果；检查手机、桌面及微信 WebView。不得用离线 mock 代替隐私或多人联机测试。
- 端到端：真实多账号、多浏览器上下文走创建、选工具、入座、开始、并发抽牌、固定骰子、重连、身份重开、观众进入、主动结束和再次开始；使用账号保存/载入方案。按项目单 spec CI 流程执行并核实运行结果。
- 平台回归：现有游戏的座位、资料、机器人、奖励、完成统计、生成器不同 profile、注册和目录契约；按实际变更执行各包最小相关测试、typecheck、lint、format 和生成器契约，CI 执行完整门禁。

验收必须检查数据内容和结果，不以“按钮存在”或构建通过代替：各未授权客户端的原始网络消息中不含他人私有结果；身份总量始终守恒；重试不多抽；重开身份后骰子状态保持；本次使用结束不产生奖励和玩家局数。

## 15. 依据与适用范围

仓库依据：[新游戏流程](../.agents/skills/new-game/SKILL.md)、[房间外壳契约](./room-shell-contract.md)、[引擎能力定义](../packages/game-engine/src/platform/engine/types.ts)、[命令回执](../packages/api-worker/src/platform/commands/CommandReceipts.ts)、[账号认证](../packages/api-worker/src/features/auth/tokenAuth.ts)和本文各节链接；以实际代码与契约为准。

查证于本次设计时的公开资料，不以发布日期本身当设计理由：

- [Cloudflare Durable Objects WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)：休眠和连接生命周期适用于实时恢复设计；连接附件不能代替断线后仍保留的成员记录。
- [Cloudflare D1 limits](https://developers.cloudflare.com/d1/platform/limits/) 和 [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)：存储行和请求体有提供方边界，应按实际套餐核实并留出余量。
- [Cloudflare D1 `batch()`](https://developers.cloudflare.com/d1/worker-api/d1-database/)：批次中的语句作为事务执行，失败回滚；不能因此假设 D1 与 DO 是同一个事务。
- [MDN `crypto.getRandomValues()`](https://developer.mozilla.org/docs/Web/API/Crypto/getRandomValues)：提供密码学强随机值，但不能据此把现有 32 位 seeded RNG 宣称为密码学安全或严格无偏。
- [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 和 [Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)：逐请求验证权限、记录可关联的事件，同时避免记录令牌及敏感内容。
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 和 [状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)：状态不只靠颜色，并使重要动态反馈对辅助技术可用。
