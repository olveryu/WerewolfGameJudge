# 管理后台重做与 D1 读取治理

> 状态：已实施，待合并部署与生产观察。日期：2026-11-11。
> 范围：`packages/api-worker/src/features/admin/`、`packages/web/src/routes/admin/`、`packages/web/src/features/admin/`，外加两个只建索引的 D1 迁移。
> 本文的生产「实测」来自 Cloudflare D1 控制台；本地回归使用真实 D1 `meta.rows_read`。第 4.5 节的单次和每日数字仍是估算，不代表上线后的实测降幅。
> 整合 main 新增的独立维护模式后，实际交付为登录与九个后台页面；维护设置同样采用新控制台，R2 存储与访客维护页行为保持不变。

## 1. 背景与证据

### 1.1 事故

2026-11-11，账号用完了 D1 免费额度的每日 500 万行读取。之后所有 D1 查询报错（错误码 7500），`main` 的两次部署都在 `Apply D1 migrations` 一步失败。额度在每天 00:00 UTC 重置。

「读行数」是 D1 的计量单位：一条查询扫描过的行数（包括索引项），不是返回的行数。

### 1.2 读取分布（实测）

数据来自 D1 控制台 Metrics 页的查询表，截至 2026-11-11 22:40 UTC 的 24 小时，共 136 条查询，合计 481 万行。

| 来源                          | 读行数    | 占比 |
| ----------------------------- | --------- | ---- |
| 管理后台                      | 约 468 万 | 97%  |
| 旧抽词查询（PR #394 已替换）  | 约 5.6 万 | 1.2% |
| 补词工作流与清理任务          | 约 4 万   | 0.8% |
| 玩家请求与每 5 分钟的定时任务 | 约 2.3 万 | 0.5% |
| 一次性迁移（0067 等）         | 约 1.2 万 | 0.2% |

读行数最高的 9 条查询全部来自管理后台，合计 460 万行：

| 查询                           | 次数 | 每次读行数 | 合计    |
| ------------------------------ | ---- | ---------- | ------- |
| 瞎掰王「各查询产出榜」         | 18   | 13.5 万    | 243 万  |
| 用户列表（按注册时间取 50 人） | 21   | 2.9 万     | 60.6 万 |
| 活跃用户数                     | 39   | 9665       | 37.7 万 |
| 节点分布                       | 39   | 9659       | 37.7 万 |
| 新注册数                       | 23   | 9653       | 22.2 万 |
| 国家分布                       | 23   | 9653       | 22.2 万 |
| 你画我猜分类产出榜             | 1    | 20.3 万    | 20.3 万 |
| 活跃用户累计局数               | 10   | 9632       | 9.6 万  |
| 用户总数 `count(*)`            | 7    | 9641       | 6.7 万  |

### 1.3 根因

1. **缺索引。** 查询计划（按迁移文件建的空库上用 `EXPLAIN QUERY PLAN` 确认）显示：
   - 瞎掰王产出榜对每个批次都按 `status = 'active'` 把整张 `fib_words` 读一遍，读行数是「批次数 × 在库词数」。
   - 你画我猜和谁是卧底的产出榜同理，读行数是「批次数 × 已通过候选数」。
   - `users` 没有 `created_at` 和 `updated_at` 的索引，用户列表和统计页的每条查询都扫全表（约 9650 行）。
2. **多余的查询。**
   - `verifyAdminPassword` 用 `/admin/stats` 验证密码（[adminAuth.ts](../packages/web/src/features/admin/services/adminAuth.ts)）。每次验证跑 5 条全表查询，约 4.8 万行；每次打开后台都会验证一次，房间标题的调试手势也会。
   - 你画我猜和谁是卧底的产出榜算出来以后页面并不显示：`GamesTab` 只在瞎掰王下渲染这一节。
   - 用户列表每次翻页、换排序、换筛选都重算一次 `count(*)`。
3. **页面重复请求。** `UsersTab`、`RoomsTab`、`GamesTab` 的查询都是 `staleTime: 0, gcTime: 0`，而全局 `QueryClient` 没有关闭 `refetchOnWindowFocus`。结果是切换标签、窗口重新获得焦点都会重新查询。用户搜索框每次停顿 300ms 就发一次请求，每次两条全表查询。

打开一次后台（验证加默认的用户页）约读 8.7 万行；打开一次瞎掰王词库页约 14 万行，你画我猜词库页约 20.5 万行。

### 1.4 现有界面的问题

以下来自代码和用模拟数据渲染出的实际页面（桌面宽度）。

- **手机单列直接放大。** 样式里没有任何断点，内容区最宽 600px（`--size-max-content-width`），桌面上两侧大片留白。
- **信息密度过低。** 用户是每人一张大卡片，每张卡片带一个「发放奖励」大按钮，一屏只能看到 4 个人，一页 50 人要滚很久。请求页有 12 张指标卡，两张一行排 6 行。
- **操作压过数据。** 词库页一进来是四个整行大按钮，其中两个是红色的「强制补词」，再下面是整行的「刷新统计」，数据在第二屏。
- **没有总览，没有层级。** 7 个标签平铺，默认落在用户页。「游戏」标签其实只有词库。
- **状态不在地址里。** 标签、筛选、页码都是组件内状态，刷新就丢，浏览器后退直接离开后台。
- **文案和格式不统一。** 标题是英文「Admin Portal」；房间的游戏显示原始 id（`werewolf`）；时间有的是截断的 UTC 字符串，有的精确到秒；「Colo」「TTFR」未解释。
- **搜索提示与行为不符。** 输入框写「搜索昵称或邮箱」，后端只按昵称查。
- **没有退出入口**，也看不到数据是什么时候取的。
- **视觉语言过时。** 整套后台沿用游戏端的手机卡片样式：大圆角白卡片、整行实心大按钮、居中的灰色小字说明、带图标的大号指标卡。没有深色模式，数字不对齐，表格是浏览器默认样式。

## 2. 目标与非目标

目标：

1. 同样的使用频率下，管理后台的 D1 读取从每天约 468 万行降到 20 万行以内（估算）。
2. 任何一个后台接口的读行数都不随用户总数或词库大小线性增长；例外逐条列在 4.5，并有上限说明。
3. 全部后台页面（登录页加 9 个页面）按第 5 节的视觉方向重做；后台沿用网站浅色主题和共享页头，不增加独立深色模式，保留现有移动端业务范围。
4. 有回归护栏：读行数测试，以及后台里能看到当天的 D1 用量。

非目标：

- 不改玩家请求、定时任务和补词工作流的查询。它们合计约占 1.3%，每次请求读 1 到 8 行。
- 不引入汇总快照表、KV 或 Cache API。治理之后词库页每次约读几千行，快照会多出一套写入和过期逻辑。词库页单日超过 50 万行时再评估。
- 不改管理员鉴权方式（仍是 `X-Admin-Token` 密码）。
- 不新增前端依赖。图表全部重画，但用手写的 SVG 和 CSS 实现，不引入图表库。
- 不改游戏端的视觉。后台语义变量映射到网站的 `colors.ts`，后台页面不再另设颜色体系。
- 不兼容旧版客户端：部署后需要刷新后台页面。

## 3. 已定决策

| 决策               | 结论                                                                       | 代价                                       |
| ------------------ | -------------------------------------------------------------------------- | ------------------------------------------ |
| 用户列表的总数     | 去掉精确总数，改为「上一页 / 下一页」                                      | 看不到「总用户: N」和总页数                |
| 按等级、局数排序   | 加索引，从 `user_stats` 出发查询                                           | 这两种排序下不显示没有战绩记录的用户       |
| 用户搜索           | 按回车或点按钮才搜索；含 `@` 时按邮箱精确匹配，否则按昵称包含匹配          | 昵称搜索最坏仍扫全表，但只在明确提交时发生 |
| 页面数据刷新       | 5 分钟内不重复请求，窗口获得焦点不自动刷新，每页有手动刷新和「更新于」时间 | 数据最多滞后 5 分钟，除非手动刷新          |
| 两个不显示的产出榜 | 删除你画我猜和谁是卧底的产出榜查询                                         | 无：分类表已有「产出 / 批次」列            |

## 4. 后端：读取治理

### 4.1 迁移 `0071_admin_read_indexes.sql`

```sql
CREATE INDEX idx_fib_words_generation_cycle ON fib_words(generation_cycle_id);
CREATE INDEX idx_users_created ON users(created_at, id);
CREATE INDEX idx_users_updated ON users(updated_at, id);
CREATE INDEX idx_user_stats_level ON user_stats(level, user_id);
CREATE INDEX idx_user_stats_games_played ON user_stats(games_played, user_id);
PRAGMA optimize;
```

- 索引第二列是主键，供 4.3 的游标分页做稳定排序。
- 普通索引只写在迁移里，不进 `dbSchema.ts`（与 `0066_d1_cleanup_indexes.sql` 的做法一致）。
- 不给候选表加 `claimed_pack_id` 索引：唯一需要它的两条产出榜查询在 4.3 里删除。
- 写入成本：过去 24 小时共写 1.6 万行（免费额度 10 万行/天）。新索引让 `users.updated_at` 和战绩更新各多写索引项，估算每天多几百行。
- 以后若有迁移重建 `users`、`user_stats` 或 `fib_words`（表复制模式），必须同时重建这些索引。
- 同步更新 `packages/api-worker/AGENTS.md` 里的迁移文件数量和末尾文件名。

### 4.2 接口变更一览

| 接口                                           | 变更                                                                                   |
| ---------------------------------------------- | -------------------------------------------------------------------------------------- |
| `GET /admin/session`                           | 新增。只过 `requireAdmin`，返回 204，不读 D1                                           |
| `GET /admin/users`                             | 改为游标分页；去掉 `page`、`total`；搜索参数改名并改语义                               |
| `GET /admin/users/countries`                   | 新增。通过国家索引逐个 seek，返回有用户的全部两位大写国家码，不扫描用户总量            |
| `GET/POST /admin/games/words/automatic-supply` | 新增。逐游戏读取／保存自动供给开关，配置在现有 R2 中，不读写 D1；调度器实际遵守该设置  |
| `GET /admin/stats`                             | 响应不变；5 条查询改为 2 条                                                            |
| `GET /admin/games/words/stats`                 | `queryLeaderboard` 只有瞎掰王返回内容，其余两个游戏返回空数组；Tavily 用量改为范围查询 |
| `GET /admin/d1-usage`                          | 新增。当天账号级 D1 读写行数，数据来自 Cloudflare GraphQL，不读 D1                     |
| `GET /admin/rooms` 及其余接口                  | 不变                                                                                   |

`/admin/rooms` 不改的原因：房间表是短期目录，实测每次约 400 行，`count(*)` 约 53 行。

客户端的 `adminResponseCodec.ts` 是严格解码（字段必须完全一致），接口和解码必须在同一个 PR 里改。

自动供给接口返回 `{ game, enabled, available }`：`enabled` 是 R2 保存的调度意愿，
`available` 直接来自该游戏的部署环境开关，不依赖 D1 库存或额度查询，也不写入 R2。
前端独立加载设置；库存查询失败仍明确显示错误，但不阻止管理员暂停／恢复自动供给。
保存成功后先取消该游戏仍在进行的设置读取，再写入服务端响应，避免保存前或保存期间发起的旧刷新覆盖新状态。

### 4.3 各接口细节

**`GET /admin/session`**

`verifyAdminPassword` 改为请求它：2xx 为有效，401 / 403 为无效。`AdminPage` 的挂载验证和 `useRoomTitleActions` 的调试手势都走这个函数，无需各自改动。

**`GET /admin/users`**

请求参数：

| 参数      | 取值                                                        | 说明                                         |
| --------- | ----------------------------------------------------------- | -------------------------------------------- |
| `sort`    | `created_at`（默认）、`updated_at`、`level`、`games_played` |                                              |
| `order`   | `desc`（默认）、`asc`                                       |                                              |
| `type`    | `registered`、`anonymous`，可省略                           |                                              |
| `country` | 两位国家码，可省略                                          |                                              |
| `q`       | 搜索词，可省略                                              | 含 `@` 按邮箱精确匹配，否则昵称 `LIKE '%q%'` |
| `cursor`  | 上一次响应的 `nextCursor`，可省略                           | 不透明字符串；格式不对返回 400               |

响应：`{ users: AdminUser[], nextCursor: string | null }`。服务端取 `limit + 1` 行判断是否有下一页，`limit` 固定 50。

游标是排序值和用户 id 的编码。查询用行值比较，直接落在索引上（已用 `EXPLAIN QUERY PLAN` 确认走 `idx_users_created`）：

```sql
SELECT ... FROM users u LEFT JOIN user_stats s ON s.user_id = u.id
WHERE (u.created_at, u.id) < (?, ?)        -- 仅带游标时
ORDER BY u.created_at DESC, u.id DESC LIMIT 51
```

`sort` 为 `level` 或 `games_played` 时从 `user_stats` 出发 `INNER JOIN users`，按 `(level, user_id)` 或 `(games_played, user_id)` 排序和取游标。

读行数说明：

- 无筛选时约为 `3 × 51`（索引项、用户行、战绩行）。
- 带 `type`、`country` 或昵称搜索时，SQLite 按索引顺序逐行过滤，直到凑满 51 行。命中越稀疏读得越多，最坏是整张表（索引项加行，约 2 万行）。这是 4.5 里唯一随用户数增长的路径，只在明确提交筛选或搜索时发生。
- 邮箱搜索走 `users.email` 的唯一索引，读 1 到 2 行。

**`GET /admin/stats`**

两条查询代替五条：

```sql
-- 新注册数：只读索引
SELECT COUNT(*) FROM users WHERE created_at >= ? AND created_at < ?;

-- 活跃用户：一次扫描取出人数、局数、国家和节点
SELECT u.last_country, u.last_colo, COUNT(*) AS users,
       COALESCE(SUM(s.games_played), 0) AS games
FROM users u LEFT JOIN user_stats s ON s.user_id = u.id
WHERE u.updated_at >= ? AND u.updated_at < ?
GROUP BY u.last_country, u.last_colo;
```

活跃数、累计局数、国家分布、节点分布在 Worker 里由第二条的结果汇总，响应字段不变。读行数约为「范围内新注册数 + 3 × 范围内活跃用户数」。

**`GET /admin/games/words/stats`**

- 删除 `getDrawGuessWordStats` 和谁是卧底对应函数里的 `boardRows` 查询，`queryLeaderboard` 返回空数组。
- 瞎掰王的产出榜查询不改，靠 `idx_fib_words_generation_cycle` 把每个批次的读取从「全部在库词」降到「该批次的词」。
- Tavily 用量把 `pack_id LIKE '2026-11-%'` 改成主键范围 `pack_id >= '2026-11-' AND pack_id < '2026-11.'`（`.` 是 `-` 的下一个字符），只读当月的行。

**`GET /admin/d1-usage`**

查询 Cloudflare GraphQL 的 `d1AnalyticsAdaptiveGroups`，按当天 UTC 日期取 `sum { rowsRead rowsWritten }`，不带 `databaseId`（免费额度按账号计）。响应：

```ts
{
  day: string;
  rowsRead: number;
  rowsWritten: number;
  rowsReadLimit: 5_000_000;
  rowsWrittenLimit: 100_000;
  generatedAt: string;
}
```

实现放进现有的 `features/admin/providers/workerAnalytics.ts`，与 Worker 调用量查询共用同一个 GraphQL 传输和 `CF_API_TOKEN`。这样允许宽松 `z.object` 的文件清单（`contracts/architecture.contract.test.ts`）不用变。

### 4.4 查询模块拆分与读行数测试

`features/admin/routes.ts` 现在把查询直接写在路由处理函数里，无法单独度量。把用户目录、增长统计拆成接收 `D1Database` 的函数（例如 `userDirectory.ts`、`growthStats.ts`），路由只做参数解析和响应映射。`gameWords.ts` 已经是这个形状。

读行数测试复用 `packages/api-worker/test/rowCountingDb.ts`（抽词测试已在用），每个用例先造两种规模的数据，断言读行数不随规模变化：

| 用例                                | 断言                                                                |
| ----------------------------------- | ------------------------------------------------------------------- |
| 用户列表，四种排序 × 升降序，无筛选 | 500 人和 5000 人时读行数相同，且不超过 `4 × 51 + 8`                 |
| 用户列表翻到第 3 页                 | 与第 1 页读行数相同                                                 |
| 邮箱搜索                            | 不超过 8                                                            |
| 增长统计                            | 只随范围内的用户数变化，范围外用户增加 10 倍不变                    |
| 瞎掰王词库统计                      | 批次数不变、在库词增加 10 倍时，产出榜读行数不按「批次 × 词数」增长 |
| 你画我猜、谁是卧底词库统计          | 候选数增加 10 倍时读行数的增量不超过新增行数的常数倍                |
| `/admin/session`                    | 0                                                                   |

## 5. 前端：管理后台重做

### 5.1 视觉方向

后台采用紧凑的「数据工作台」视觉，参照主流开发者控制台的密度与层级；同时遵循网站现有的浅色主题和共享页头。保持后台信息架构与既有移动端布局，不额外扩展手机功能。

| 方面       | 现在                                   | 重做后                                                                                          |
| ---------- | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 画布与层次 | 灰底上叠大圆角白卡片                   | 中性浅灰画布；内容放在面板上，面板之间只用 1px 细线区分，不用投影；只有抽屉和菜单这类浮层带阴影 |
| 颜色       | 紫色实心大按钮、红色实心大按钮随处可见 | 中性色为主。强调色只有一个（沿用品牌靛紫），只用于当前导航项、主按钮、链接和图表主序列          |
| 语义色     | 无                                     | 正常、注意、异常三种，只出现在状态标签和用量条上，并且总是带文字                                |
| 主题       | 网站使用浅色主题                       | 复用网站的浅色主题 token；不增加深色模式或独立主题偏好                                          |
| 字号       | 沿用游戏端的手机字号                   | 正文 14px，表格 13px，辅助说明 12px；大数字 26px 半粗、收紧字距                                 |
| 数字       | 比例字体，不对齐                       | 全部用等宽数字（`tabular-nums`）并右对齐；用户 ID、房间号、路由用等宽字体                       |
| 密度       | 每个用户一张大卡片，一屏 4 人          | 表格行高约 40px；面板内边距 16 到 20px                                                          |
| 圆角       | 大圆角卡片                             | 面板 14px，控件 8 到 10px，状态标签全圆角                                                       |
| 按钮       | 整行实心按钮                           | 每页最多一个实心主按钮；其余是描边按钮、图标按钮或文字链接；危险操作须明确确认                  |
| 指标       | 图标 + 大号紫色数字的卡片              | 桌面自动换列，手机单列横排；长数值缩写，点击可看完整值，说明可换行                              |
| 图表       | 只有条形图和一条折线                   | 面积趋势图（渐变填充）、环形用量图、横向条形列表、分类库存热力格                                |
| 图标       | 标签栏用图标加文字的大格子             | 沿用现有的 ion 描边图标（`~icons/ion/*`），统一 16px，只出现在导航和图标按钮里                  |
| 动效       | 无                                     | 悬停和按下 100 到 150ms；抽屉滑入 200ms；系统开启「减少动态效果」时全部关闭                     |

四条行为原则贯穿所有页面：

1. **数据优先。** 一屏先看到数字和表格；操作收进工具栏和菜单。
2. **桌面是表格，手机是紧凑行。** 同一份数据两种排布。
3. **状态在地址里。** 页面、子页、筛选、排序都可刷新、可后退。
4. **不偷偷花额度。** 页面不自动重新请求；每页显示「更新于 HH:MM」和刷新按钮。

可交互的基础能力（对话框、菜单的焦点管理）继续用 Ark UI，确认框继续走 `showAlert`；后台语义变量映射到网站主题色（见 5.8），页头复用网站的 `ScreenHeader`。

### 5.4 数据获取策略

新增 `features/admin/queries/adminQueryOptions.ts`，是后台所有查询的唯一出口，统一设置：

- `staleTime: 5 分钟`、`gcTime: 10 分钟`：切换页面再切回来直接用缓存。
- `refetchOnWindowFocus: false`、`refetchOnReconnect: false`、`retry: false`。
- 查询键以 `['admin', 页面, 参数]` 为形状，手动刷新只重新请求当前挂载且启用的后台查询。

各页不再自己写 `staleTime: 0`。补词触发成功后不自动刷新统计（工作流要几分钟才有结果），只提示「已触发，稍后手动刷新」。

维护配置例外：沿用独立维护功能的 30 秒新鲜期，开启维护时每 30 秒重读以反映自动恢复；这些读写走 R2，不读 D1。

### 5.7 状态、无障碍与格式

- 加载用骨架屏占住最终布局，不再是页面中央一个转圈；刷新时保留旧数据并在「更新于」旁显示进行中。
- 错误显示原因和「重试」；鉴权失败（401 / 403）清除凭据并回到登录。
- 导航是 `<nav>` 加当前页的 `aria-current`；表格用真实的 `<table>`、`<th scope>`；排序列有 `aria-sort`；抽屉和菜单的焦点管理交给 Ark UI。
- 状态不只靠颜色：`StatusBadge` 和 `Meter` 都带文字。
- 手机上可点区域不小于 `--size-min-touch-target`。
- 时间统一：一天内显示相对时间，更早显示本地日期；完整的本地时间放在 `title`。数字用千分位。
- 文案：标题「Admin Portal」改为「管理后台」；Colo 写作「节点」；房间的游戏显示中文名。
- 文字与背景的对比度按网站现有浅色主题检查，不引入深色主题。

### 5.8 样式与体积

- **后台语义别名。** 后台变量定义在后台根节点，但都映射到 `colors.ts` 发布的网站 `--color-*` 色值；后台样式只引用这些别名和 `tokens.css` 里的尺寸变量，不维护另一套调色板。
- **尺寸。** 指标最小列宽、内容最大宽度、表格行高、面板圆角等变量加进 `theme/tokens.css`；媒体查询断点直接写在后台样式内，CSS 自定义属性不能用于媒体查询条件。
- **契约测试。** `noHardcodedStyleValues` 会拦截样式里的颜色字面量和像素值，新变量的定义位置和前缀要让这个测试认可；实施时先读它的规则，再决定变量放在 `colors.ts` 还是 `tokens.css`。
- **主题偏好。** 后台不读取系统颜色偏好、不保存主题选择；跟随网站当前浅色主题。
- 现在的 `AdminPage.css`、`AdminTabs.css`、`AdminComponents.css`（共约 950 行）整体删除，新样式从零写，不在旧样式上叠加。
- 全站代码是一个体积预算（`packages/web/scripts/check-bundle-size.mjs`，余量约 4%）。重做不加依赖，旧的后台代码同步删除；`pnpm --filter @game-judge/web run build` 会检查。

## 7. 风险与回退

| 风险                                            | 应对                                                                                                                        |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 生产库的查询计划与空库不同                      | 迁移末尾执行 `PRAGMA optimize`；上线后在 D1 控制台核对前 10 条查询；读行数测试跑在 Workers 测试运行时自带的 D1 上，不是模拟 |
| 迁移本身消耗读取                                | 建索引会读一遍相关表（估算共约 3 万行），在额度重置后部署                                                                   |
| Worker 先于前端部署的几分钟内，旧前端调用新接口 | 用户目录响应不兼容旧客户端；Worker 和前端同次发布，完成后刷新后台。过渡期明确报错，不做旧格式伪兼容                         |
| `CF_API_TOKEN` 没有 Account Analytics 读取权限  | 现有的 Worker 调用量查询用同一个 GraphQL 接口；上线时确认 D1 权限；失败时其他总览面板仍独立可用                             |
| 带稀疏筛选的用户查询仍可能读到全表              | 只在明确提交时发生；总览页的 D1 用量条能看到影响                                                                            |
| 回退                                            | Worker 与前端一起回滚；索引迁移不回滚（多余的索引只增加少量写入）                                                           |

## 8. 本次保留的口径

1. **「总局数」的口径。** 仍是「范围内活跃过的用户的累计局数之和」，不是范围内打了多少局；标签和说明已改准确。
2. **国家筛选的选项。** 「全部国家」加上实际有用户的所有国家，不再固定 CN / US。只在打开选择面板时查询，复用五分钟缓存。迁移 `0072_admin_country_options.sql` 为有效两位大写国家码建立覆盖部分索引；递归查询从上一个国家 seek 到下一个国家，忽略空值、空串与非国家码，读取随国家数而非用户数增长。真实 D1 测试中，CN / JP / US 三个国家在 500 / 5000 用户下读取量不变，单次不超过 16 行。建索引有一次性用户表读取和后续地区更新索引写入成本；不增加汇总表或后台轮询。
3. **自动供给开关。** 三个词库分别保存设置，使用现有 `GAME_MEDIA` R2 桶，不新增 D1 表、迁移或轮询。未配置时保留原定时行为；部署环境开关仍是上层限制。关闭只阻止以后的每日自动任务，不取消已启动任务、不禁用手动补词。配置损坏或读取失败时明确报错，不默认为开启；保存失败时界面保持原状态。切换只更新该设置的缓存，不重新查询库存。
