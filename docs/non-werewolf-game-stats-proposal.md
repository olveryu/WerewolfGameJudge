# 各游戏战绩统计、结算人数门槛与你画我猜互动

> 状态：已实施，本地范围验证通过；尚未部署生产数据库迁移或运行 CI E2E
> 最后核对：2026-11-12（文中「现状」指实施前基线，当前验证范围见 §7）

## 1. 已定的产品决定

| 主题         | 结论                                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 范围         | 阿瓦隆、你画我猜、瞎掰王、你画我猜接龙、谁是卧底、故事接龙新增个人战绩。狼人杀同步优化统计读写，阵营统计口径和 2 小时延迟不变。`demo` 没有战绩 |
| 计入条件     | 只有正常打到终局、且真人数达到门槛的对局才结算。中止、过期、没打完的都不算                                                                     |
| 人数门槛     | 狼人杀 6 人（现状）。其余游戏为各自的最少人数。不达标的对局没有经验、没有奖励、不计战绩，也不计总局数                                          |
| 阿瓦隆       | 终局即记录、即显示，没有延迟                                                                                                                   |
| 你画我猜互动 | 鲜花、鸡蛋、番茄。每人每回合一次、三选一。作画中和回合结算展示时都能送。显示是谁送的。不影响得分。个人战绩显示累计收到的三种数量               |
| 展示位置     | 房间里的玩家资料卡显示当前游戏的战绩。设置页「战绩」用游戏选择卡切换，默认狼人杀                                                               |
| 不做         | 跨游戏总分、总胜率、任何排行榜                                                                                                                 |

## 2. 结算人数门槛

现状：狼人杀的结算在 Worker 里要求 6 个真人（[settleGameResults.ts](../packages/api-worker/src/games/werewolf/settlement/settleGameResults.ts) 的 `MIN_HUMAN_PLAYERS`）。其余游戏的奖励结算不看人数（[settleGameRewards.ts](../packages/api-worker/src/features/account/settleGameRewards.ts)），一个真人加机器人打完也会发经验和奖励，并计入总局数。本方案改掉后者。

| 游戏         | 最少真人数 | 来源                           |
| ------------ | ---------: | ------------------------------ |
| 狼人杀       |          6 | 现有 `MIN_HUMAN_PLAYERS`，不改 |
| 阿瓦隆       |          5 | `AVALON_MIN_PLAYERS`           |
| 你画我猜     |          4 | `DRAWGUESS_MIN_PLAYERS`        |
| 瞎掰王       |          4 | `FIB_MIN_PLAYERS`              |
| 你画我猜接龙 |          4 | `PICTIONARY_MIN_PLAYERS`       |
| 谁是卧底     |          4 | `UNDERCOVER_MIN_PLAYERS`       |
| 故事接龙     |          4 | `STORY_RELAY_MIN_PLAYERS`      |

口径：

- 真人指已入座、非机器人的座位。匿名（游客）真人计入人数，但只有注册账号拿奖励和战绩。这是狼人杀的现行口径（[growth-system-design.md](growth-system-design.md) §2），六款游戏沿用。
- 你画我猜接龙和故事接龙按本轮冻结的真人名单计数，不按「有实际提交的人」计数。这两款的奖励名单是过滤掉整局没提交的人之后的结果，拿它数人头会把「4 个真人、1 人没交」误判成不达标。
- 狼人杀 MVP 奖励已有自己的 6 人规则，不动。

## 3. 各游戏战绩

所有数字都取自游戏过程中记录、并保留到终局的事实；缺少的记录在对应状态转移中补齐，不从终局结果猜算。房主接管机器人座位做的操作归机器人座位，不算到任何人头上。

| 游戏         | 显示的战绩                                                                                                                                    | 取自                                                                         |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 阿瓦隆       | 完成局数；好人、坏人各自的局数与胜率；各身份的局数与胜率                                                                                      | 座位身份、终局胜方                                                           |
| 你画我猜     | 完成局数；猜词次数；猜中率（猜中的回合 ÷ 自己不是画手的回合）；平均猜中用时；作画回合数与被猜中的作画回合数；累计得分；收到的鲜花、鸡蛋、番茄 | `turnHistory` 的画手、猜中座位、猜词次数、猜中用时和互动，终局 `totalScores` |
| 瞎掰王       | 完成轮数；大聪明、老实人、瞎掰王各当了几轮；当大聪明时找出老实人的轮数；当老实人时被找出的轮数；当瞎掰王时被误选的次数                        | 本轮身份分配、房主代点的座位记录                                             |
| 你画我猜接龙 | 完成局数；写词次数；作画次数                                                                                                                  | 各接龙链里本人的条目                                                         |
| 谁是卧底     | 完成局数；平民、卧底、白板各自的局数与胜率                                                                                                    | 本轮身份、终局胜方（身份与胜方相同记胜）                                     |
| 故事接龙     | 完成局数；写下的段落数                                                                                                                        | 各接龙链里本人的文字条目                                                     |

瞎掰王以轮为单位，因为它一轮结算一次；游戏本身不计分，所以没有胜率。两款接龙是创作游戏，没有胜负。

阿瓦隆仅统计局数及阵营、身份胜率，不统计上任务、任务成功、队长提案或提案通过。任务结果与提案投票不能直接归因为个人能力，且任务成功不一定符合坏人阵营的目标。

你画我猜新增指标口径：

- 猜词次数：引擎接受的猜词提交次数，包含猜对和猜错；无效输入、限流拒绝、过期命令等未被接受的提交不计入。
- 猜中用时：从该回合作画开始到首次猜中，使用引擎时间戳计算；不从玩家第一次猜词开始计时，也不受猜中后缩短倒计时影响。个人战绩显示平均猜中用时，未猜中的回合不进入平均值，没有猜中记录时显示「—」。
- 每回合按座位保存猜词次数与猜中用时，不为统计保留猜词正文。账户累计保存猜中用时总和与有用时记录的猜中回合数，读取时计算平均值，不累加平均值。

不纳入本次范围：

- 两款接龙的「未提交次数」「空提交次数」和谁是卧底的「存活至结算次数」，按用户决定不恢复。
- 六款新增统计的历史回填。以前的对局没有留下这些事实，战绩从上线后的第一局算起。狼人杀已有阵营记录必须保留，并按 §5.2.2 归并，不能清零重算。

## 4. 你画我猜互动

- 谁能送：沿用现有座位操作和房主接管规则，画手本人除外。不新增机器人座位禁止互动的限制。
- 何时送：当前回合的作画阶段和回合结算展示阶段。
- 送几次：每人每回合一次，三选一，送出后不能改。
- 送给谁：当前回合的画手。画手是机器人座位时房间里照常显示，但不计入任何人的战绩。
- 可见性：全房可见谁送了什么，以及画手本回合收到的三种数量。
- 影响：不改变得分、倒计时和回合推进。
- 计入战绩：回合记录随 `turnHistory` 冻结。整局正常完成并通过人数门槛后，按画手汇总进个人战绩。

界面要求：三个按钮用带文字标签的 SVG 图标，触控区域不小于 44px，可用键盘操作；送出后本人按钮呈已选且不可再点；动效不遮挡画布、猜词输入和倒计时，系统开启「减少动态效果」时改为静态反馈；样式值走主题 token。

## 5. 实现设计

### 5.1 引擎

- 门槛在引擎里判定。[completionEffect.ts](../packages/game-engine/src/platform/engine/completionEffect.ts) 的 `buildGameCompletionPayload` 是所有游戏完成事件的唯一装配点，并且拿得到过滤前的真人名单。给它加一个必填的 `minimumHumanPlayers`，人数不足时返回 `null`，调用方不发完成 effect。各游戏传自己的最少人数常量。`demo` 是生成器模板的参照，随之修改，生成器模板同步。
- Worker 不再重复数人头。完成 effect 不存在就没有奖励、战绩和总局数。
- 每款游戏的完成 effect 增加按用户的战绩事实（一人一条，字段由该游戏定义），由纯函数从终局状态算出。
- 战绩事实必须从**应用终局事件之后**的状态计算。现在的完成 effect 是用事件应用前的状态构造的（例如 [drawguess/engine.ts](../packages/game-engine/src/games/drawguess/engine.ts) 里 `completionEffect(state, context)` 与终局事件同时产出），而你画我猜最后一个回合的记录、阿瓦隆的胜方都是终局事件才写入的。狼人杀的做法是先把事件归约成新状态再建 effect（[werewolf/engine.ts](../packages/game-engine/src/games/werewolf/engine.ts) 的 `finalizeWerewolfDecision`），六款游戏照此处理。
- 你画我猜逐次累计引擎接受的猜词提交，并以引擎保存的作画起点计算首次猜中用时。计数和用时随回合结算状态保留，再冻结进 `turnHistory`，不靠可能被截断的聊天记录反推，也不为统计额外保留猜词正文。
- 你画我猜新增命令 `drawguess.reaction.send`，沿用现有回合命令的 `phaseRevision` 加 `turnIndex` 绑定。作画和回合结算两个阶段各带一个「送出座位 → 种类」的记录，回合结算关闭时冻结进回合记录。一个字段同时承担一人一次的判定和署名展示，数量由它派生，不另存计数。互动不推进 `phaseRevision`。
- 你画我猜状态版本 4 → 5，`migratePersistedDrawGuessState` 增加 v4 升级：已有阶段和回合记录补空的互动记录；作画阶段已有猜词数据继续正常提取，旧的回合结算状态及历史记录缺少的猜词统计标为未采集，不伪造为零，也不计入平均猜中用时的分母。
- 六款新增统计游戏的 `publicStats.ts` 从实施前仅带 `gameType` 的空壳扩展为各游戏响应类型和严格解析器；狼人杀保留现有统计字段并增加缓存到期信息。

### 5.2 Worker

#### 5.2.1 六款新增游戏统计

- 六款游戏各一张按用户累加的计数表，归属该游戏的 `dbSchema.ts`，`user_id` 外键 `ON DELETE CASCADE`。阿瓦隆和谁是卧底按身份分行（主键为用户加身份），阵营由身份推导，不另存。
- 不新增逐局统计流水。资料卡每次点开都要读，流水表的读行数会随局数增长；计数表按主键或主键前缀读取。普通游戏最多一行，阿瓦隆、谁是卧底最多为已定义的身份种类数，而不是历史局数。
- 写入与奖励账本在同一个 D1 batch 里，排在「插入奖励结果行」之后、「标记 `stats_applied`」之前，条件是该用户本次的结果行 `stats_applied = 0`。这与 `user_stats` 累加用的是同一个幂等边界（[settlementLedger.ts](../packages/api-worker/src/features/account/settlementLedger.ts)），重放不会重复累加，也不需要第二套去重。这段条件抽成 `settlementLedger` 的共用片段，各游戏只提供自己的表和增量。
- 由此得到一条不变量：一个用户在一次结算中，有奖励结果行才有战绩累加。注册账号限定、接龙的提交过滤、游客事后注册不补领，全部自动一致。
- 读取走现有的 `GET /api/games/:gameType/users/:userId/stats`，各游戏实现 `getPublicUserStats`，按主键读取后交给引擎的严格解析器。
- 按 Worker 包的 D1 规则，用 `test/rowCountingDb.ts` 给读取和结算写入各断言一个行数预算。瞎掰王一轮一结算，是写入最频繁的路径：每个注册真人每轮多写一行。
- 计数表不带 `game_type` 列，不进入注册迁移的 CHECK 重建名单。

#### 5.2.2 狼人杀：累计统计加未归并记录

现状：`camp_settlements` 每个账号、每局一条，主键是 `(user_id, settle_key)`；读取按 `datetime(settled_at) <= datetime('now', '-2 hours')` 过滤并分组。返回四个阵营不等于只读四行；聚合会读取该用户已到期的历史记录。时间字段既有生产 ISO 格式，也有旧 SQLite 格式，现有集成测试明确覆盖二者，不能改用原始字符串大小比较。

新增和调整的持久化结构：

| 结构                               | 设计                                                                                                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `werewolf_user_camp_stats`（新增） | 每用户一行，`user_id` 主键及删除级联，`wolf_count`、`god_count`、`villager_count`、`third_count` 为非负整数。仅累计已到期且已归并的记录，总局数由四项相加，不再存一份 |
| `camp_settlements`（保留）         | 新增 `is_aggregated INTEGER NOT NULL DEFAULT 0 CHECK (is_aggregated IN (0, 1))`。保留原始阵营、时间和唯一键，继续承担历史凭据和结算重放去重，已归并记录不删除         |
| 待读取部分索引                     | `(user_id, datetime(settled_at), camp) WHERE is_aggregated = 0`，用于读取指定用户已到期但未归并的记录                                                                 |
| 待归并部分索引                     | `(datetime(settled_at), user_id, settle_key) WHERE is_aggregated = 0`，用于定时任务按到期顺序取小批记录                                                               |

两个部分索引分别服务用户读取与全局归并，不能指望一个索引同时高效处理两种不同的首列条件。原 `idx_camp_settlements_user_settled` 在确认查询消费者和执行计划后由新索引替代；不无条件叠加索引。更新游戏归属的 Drizzle 声明；不要把狼人杀统计放进共享账户表。

写入、归并与读取：

1. **结算时**：沿用 [settleGameResults.ts](../packages/api-worker/src/games/werewolf/settlement/settleGameResults.ts) 的原子奖励结算及阵营记录写入。新记录为未归并状态，不能立即加到公开累计表，也不修改奖励或 MVP 的人数、时间和幂等规则。
2. **定时归并**：狼人杀模块提供归并函数，由现有 [scheduled.ts](../packages/api-worker/src/app/scheduled.ts) 的每五分钟入口组合调用。每批最多取 32 条已到期、未归并记录，并设置每次运行的批数上限，避免一次追赶全部历史。归并任务失败须按仓库日志与错误路径显式报告，不吞错，也不能因它失败而跳过房间维护。
3. **同批原子性**：候选列表只提供原始复合主键，不在 JavaScript 中预先算好增量再盲写。一个 D1 batch 内先从这些键中仍为 `is_aggregated = 0`、且符合固定截止时间的行按用户／阵营计算并累加，再将同一集合标记为已归并。两条语句使用相同键集合、过滤条件和截止时间；任一步失败全批回滚。并发任务拿到相同候选时，后执行者的源集合为空，不能再累计。未知阵营必须报错，不用 `CASE ELSE 0` 掩盖坏数据。
4. **查询时**：用**一条 SQL**在同一读取快照内返回「累计表的四项计数 + 该用户已到期但未归并记录的计数」。不能分两次请求先读累计、再读待归并，否则与归并事务交错可能重复或漏计。两小时内的记录既不归并，也不进入查询补集。本人和他人共用这一查询。
5. **准确性不依赖 cron 准点**：记录满两小时后，即使定时归并尚未执行，也由查询补集计入；不能把可见时间变成两小时加五分钟。保持现有 `datetime` 比较精度和时区语义。客户端缓存不能在阈值后继续长期展示旧结果，狼人杀统计响应应给出下一次可见变化时间，查询在到期及恢复前台时重验证；它只透露时间，不透露隐藏阵营。

成本边界：

- 稳态读取不再扫描用户全部历史，而是读取该用户的一条累计记录及已到期、未归并的小尾部；未到期记录由范围条件排除，部分索引排除已归并历史。一条累计记录是逻辑行数：当前 SQL 读取四项计数有固定次数的主键读取，物理读写以 §5.2.4 的测量为准。
- 这**不是无条件固定一行读取**：首次历史归并、cron 故障或处理能力不足时，补集会增大。读取仍须准确，不能 `LIMIT` 截断统计，也不能返回过期累计值冒充完整结果。归并吞吐要高于新增速度，并监控未归并到期记录数、最老到期记录的积压时间和失败次数。
- 每条阵营记录除原结算写入外，多一次归并标记更新；每批每个涉及用户多一次累计表 upsert。部分索引的插入／删除也有写成本，不能只数业务表更新。
- 沿用原阵营凭据不删除的策略，因此本次优化的是重复读取成本，不宣称历史存储变成常数。保留凭据可避免删掉记录后重放结算再次入账。

#### 5.2.3 D1 migration 与上线顺序

已创建 [0074_multigame_stats.sql](../packages/api-worker/migrations/0074_multigame_stats.sql)（六款累计表）和 [0075_werewolf_camp_aggregation.sql](../packages/api-worker/migrations/0075_werewolf_camp_aggregation.sql)（狼人杀累计表、归并标记及部分索引）。本地迁移后的 D1 测试已通过，尚未对生产执行。

1. 先新增六款累计表、狼人杀累计表、`is_aggregated` 列及必要索引。共新增 **7 张归属表**；不是把狼人杀改成即时累计。
2. 发布前只读核对历史行数、阵营值和时间格式，估算新索引扫描／构建的一次性读写与耗时。未知阵营或无法解析的时间须先处理，不能静默跳过。新表的字段约束、用户删除级联、复合主键、现有结算唯一键和相关索引都纳入迁移测试。
3. 历史狼人杀记录默认未归并。发布支持新结构的读写和归并代码，按与新记录相同的条件逐批归并历史；不在 migration 内一次性 `GROUP BY` 全部历史再大批更新。过程中查询仍用「累计 + 未归并到期记录」，历史统计不清零，未满两小时的历史记录继续等待。
4. migration 必须先于新 Worker 部署；旧 Worker 显式列名插入仍可使用新列默认值。保留完整流水，因此回退到仍按原查询读取、并按原唯一键插入的版本可以保持正确；归并暂停时只积压未归并记录，重新启用后继续追赶。应用回退不同时删除累计表、标记或索引；结构回退需要单独评估，不能随手清除迁移状态。
5. 索引构建仍会触碰历史数据，不能因为采用分批归并就声称迁移无成本。本次按已有序列追加 0074、0075；当前共 74 个 SQL migration 文件，归属表从 32 张增至 39 张。

#### 5.2.4 读写验证

- 使用迁移后的 D1 和 `test/rowCountingDb.ts`，分别测业务结果与 `rows_read`、`rows_written`；记录执行计划，不用“返回几行”推导费用。
- 六款新增统计覆盖首次结算、重放、并发、游客、提交过滤；普通游戏一行、阿瓦隆／卧底按身份行数，读取不随历史局数线性增长。
- 狼人杀至少对比 100 条和 10,000 条已归并历史、相同的小尾部，要求读取预算不随已归并历史增长；另测大规模未到期记录不被全扫，以及迁移积压和故障追赶时的真实成本。具体数值阈值须从实际 SQL 测量后写入测试，不能把未测的逻辑行数当作已验证预算。
- 归并覆盖空批、满批、批数上限、定时任务重试／并发、同时间戳不同结算键、批中失败回滚、用户删除级联。验证累计增量与标记集合严格一致，重放不能重新置回未归并状态。
- 保留现有本人／他人、ISO／SQLite 时间混用测试；新增两小时边界、cron 未运行时的准时可见，以及读取与归并并发时不重不漏。

狼人杀迁移后 D1 定向测试已验证以下预算（本地 `rows_read` / `rows_written`，不是生产账单）：

| 场景         | 数据规模                                                | 读取上限 | 写入上限 |
| ------------ | ------------------------------------------------------- | -------: | -------: |
| 资料读取     | 100 / 10,000 条已归并历史、同量未到期记录、1 条到期尾部 |       40 |        0 |
| 单条到期归并 | 同上                                                    |       80 |       12 |
| 单次积压归并 | 1,000 / 10,000 条到期记录，每次只处理 256 条            |    4,096 |    1,100 |

积压归并由有界候选键驱动主键查询；不以到期时间索引重扫整个积压集合。累计与标记仍在同一 batch，触发标记失败时二者一起回滚。资料读取为了不漏掉到期记录，会读取全部到期未归并尾部，故 cron 故障或历史回填期间的读取成本仍随该尾部增长，不承诺恒定。

### 5.3 Web

- 每款游戏提供一个战绩查询和一个展示组件，两处共用：房间资料卡走现有的 `gameDetails` 加 `profileDetailsRenderer`（目前只有狼人杀接了），设置页走 [catalog.ts](../packages/web/src/games/catalog.ts) 的 `AccountStats`。
- Profile 上方使用当前游戏的完成局数，不再取全局 `profile.gamesPlayed`，并去掉下方重复局数；狼人杀使用两小时可见口径，瞎掰王用轮数。局数和已解锁用紧凑数据行，已解锁展示「已拥有／可解锁总数」，分子分母必须为同一物品集合，分母口径在实施前按现有物品目录核实，不用 Mock 的示例总数。
- 七款面板统一紧凑样式：有定义的比例使用细横条和明确分母，原始计数与用时使用数据行；底部短说明居中。阿瓦隆身份细项可展开且同样使用横条，没有对局的身份显示「—」；区块边界只保留一条分隔线。保留现有资料卡的宽度及最大高度，超出时卡片内滚动。
- 设置页「战绩」现在把所有游戏的统计依次堆叠。改为单选的游戏选择卡，只挂载选中游戏的组件，所以只发一个查询。默认项由 catalog 给出（狼人杀），设置页不写死游戏字面量。选择卡用单选组语义，选中态不只靠颜色区分。
- Web 包不允许动态 import，七个组件静态引入，构建时注意设置页路由的 gzip 预算。
- 收到结算到账事件（`SETTLE_RESULT`）后，失效对应游戏的战绩查询，资料卡才能在一局结束后马上显示新数字。
- 狼人杀查询额外返回最早待可见记录的 `nextVisibilityAt`，不提前返回其阵营或数量。面板挂载时在该时刻重取，重新聚焦也重验证；不用持续轮询，也不依赖 cron 完成才刷新。
- 没有战绩的用户（游客、新用户）显示空状态，不显示一排 0% 的胜率。

人工设计与接入报告必须选择并批准奖励政策/数值、统计局/轮单位、玩法事实与归属、

或明确批准仅完成局数，不能把骨架当作玩法统计已完成。游客计人数但不入账，机器人不计人数，
